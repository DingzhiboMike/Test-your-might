# Реестр скиллов оркестратора

Оркестратор читает этот файл один раз в начале задачи и выбирает по нему. Для звеньев цепочки главное поле — «какую дыру закрывает»: где скилл стоит в маршруте. Для источников данных метод под пункт пути выбирается по полям «Отвечает на» и «Не отвечает на».

Все, кто ходит в веб, работают по `web-protocol.md`: уровни источников, отбор отчётов, запрос на опровержение, триангуляция, метки уверенности.

Свой артефакт скилл пишет сам — ровно в путь, который передал оркестратор; имя файла — из поля «Выход» ниже. Больше ничего не создаёт и не правит: ни `log.md`, ни чужие файлы, ни имена. Единственное, что он добавляет помимо артефакта, — источники в реестр задачи через `scripts/add_source.py`. Опорные фрагменты — «дословно» [F-id]: оркестратор проверяет их скриптом по сырому тексту. Оркестратору возвращает путь, короткое резюме и сигналы. Лог ведёт только оркестратор.

**Режим исправления по проверке смысла.** Если оркестратор вернул скиллу его артефакт вместе с отчётом `review-<артефакт>` от meaning-review, скилл переписывает артефакт целиком с исправлениями и в конце добавляет блок:

```
ПО ПРОВЕРКЕ СМЫСЛА
С-01 — исправлено: что именно поменял
С-02 — снято: утверждение убрано
С-03 — оспорено: почему замечание неверно — с фрагментом «…» [F-id]
```

Ответ нужен на каждое замечание с пометкой [блок]. Формат гибкий: маркер списка, жирный шрифт и метка [блок] после номера допустимы, скрипт их примет; править артефакт вручную, чтобы проверка прошла, не нужно. «Оспорено» без причины не засчитывается. Новых выводов в этом режиме скилл не добавляет.

**Режим исправления по пробному прогону.** Если оркестратор вернул автору бэклога или плана (project-analyst) или набора для проверки (test-kit) его артефакт вместе с `03c-rehearsal.md`, автор переписывает артефакт целиком и применяет раздел «СЛЕДСТВИЯ → Для эксперимента»: статус «после правки» — правка внесена; «не запускать» — тест переделан так, чтобы ветки различались, или снят с причиной. Критерии успеха и отсечения до старта менять можно — результатов ещё нет, — но только с записью «было → стало → почему». В конце — блок:

```
ПО ПРОБНОМУ ПРОГОНУ
Строка 2 — применено: что поменял; критерии: не менялись / было → стало
Строка 3 — человеку: что решить и что рекомендую
Строка 5 — отклонено: почему находка неверна для этого теста
```

Ответ нужен на каждую строку со статусом не «как есть». «Отклонено» без причины не засчитывается. Новых тестов в этом режиме автор не добавляет; «что подсказали персоны» идёт в сдачу как вопросы к живым интервью, а не в бэклог.

**Режим оркестратора.** После согласования ТЗ маршрут идёт без пауз. Скилл в режиме оркестратора не завершает ответ: отдаёт результат и возвращает управление оркестратору. Ответ человеку заканчивается только сдачей, остановкой по правилу или вопросом о втором возврате. Скиллы, которые в ручном режиме останавливаются на согласование плана поиска (market-analyze, target-audience-analyst), здесь строят план, возвращают его оркестратору в резюме и сразу ищут. В лог план записывает оркестратор.

### brief-writer — задача аналитику и бриф редактору

**Место в маршруте.** Только тип выхода «ТЗ на доработку»: финиш, один раз, после проверки по сути.

**Что делает.** Из гипотез, вердиктов, `src-*` и запросов данных собирает три коротких документа на простом языке и один служебный. `07a-analyst.md` — до десяти задач аналитику (что снять, колонки, срезы, период, «если A — …, иначе …», куда положить). `07b-editor.md` — раздел на направление (кому пишем, что хотим от клиента, главная мысль, до трёх пунктов, слова клиентов дословно, чего не писать, чего нельзя обещать). `07c-decisions.md` — до десяти решений за человеком. `07d-trace.md` — служебный: откуда что взято, номера гипотез, вердикты, id источников, дословные цитаты. В трёх первых нет номеров гипотез, id источников и слов системы: аналитик и редактор её не знают. Сбои реестра и замечания к проверкам в документы не попадают, а идут оркестратору. Не ищет, не придумывает гипотез и текстов для публикации.

**Вход.** Обязательно — ТЗ, гипотезы, вердикты проверки по сути, итоговая позиция консультанта `02e-position.md`, запросы данных D-N из лога. Желательно — `src-*`, реестры, разбор консультанта. Порядок направлений в брифе редактору и срочность задач аналитику — по итоговой позиции.

**Выход.** Файлы `07a-analyst.md`, `07b-editor.md`, `07c-decisions.md`, `07d-trace.md`.

**Какую дыру закрывает.** Гипотезы проверены, но нет документов, с которыми аналитик и редактор могут приступить к работе.

**Когда не вызывать.** Тип выхода другой. Нет вердиктов проверки по сути.

**Цена.** Средняя. Модель средняя: сборка по жёсткому формату, выводов не делает.

**Признак провала.** Номера гипотез, id или слова системы в документах для людей (`check_readable.py`). Задача аналитику без «если A — …, иначе …» или длиннее 120 слов. Раздел брифа длиннее 150 слов. Цитата в брифе не дословная или её нет в служебном файле. Сбои реестра в документах для людей. Новая гипотеза в документе.

### research-report — итоговое исследование

**Место в маршруте.** Тип выхода «исследование» — финиш, один раз, после источников данных; тип «валидация» — финиш, режим «валидация», после методов проверки, файл `06-validation.md`.

**Что делает.** Собирает отчёт из найденного: ответ на каждый пункт GAP (ответ, ответ с оговоркой, стороны, не закрыто), аргументация по карте «основания → связка → граница → контраргумент», стыки между типами источников, числа из реестра, блок «СЧЁТ ОПОР» из скрипта, карта доверия. Не ищет, не придумывает, позицию занимает только когда данные держат.

**Вход.** Обязательно — ТЗ с GAP и пометками `[ключевой]`, `src-*`, реестры `sources.csv` и `numbers.csv`, `checks/trust.md`. Желательно — журналы запросов, `review-*`.

**Выход.** Файл `06-research.md`: ответ, разделы по вопросам, стыки, позиция команды, карта доверия, что дальше.

**Какую дыру закрывает.** Материал собран, но нет отчёта, по которому можно принять решение и понять, чему в нём верить.

**Когда не вызывать.** Тип выхода другой. Нет ни одного `src-*`.

**Цена.** Средняя. Сильная модель.

**Признак провала.** Ответ в первом блоке не совпадает с разделом по вопросу. Позиция там, где исход «стороны» или «не закрыто». Контраргумент слабее источника. Число не из реестра. Блок счёта пересказан. Ключевой пункт закрыт слабо и не вынесен в карту доверия.

### meaning-review — проверка смысла

**Место в маршруте.** Не выбирается по приоритетам: вызывается там, где стоит итог, — после `02c-validation.md`, `06-research.md` и `06-validation.md`, — и после `src-*`, который закрывает ключевой пункт пути. По остальным `src-*` и по второму проходу проверки по сути не вызывается: их выводы проверяются там, где на них опирается вердикт или отчёт. В бюджет шагов тира не входит, как и проверки скриптом.

**Что делает.** Проверяет, держит ли источник то, что из него выведено: вывод не шире и не сильнее фрагмента, фрагмент подтверждает тезис, нет повторов, вывод следует из оснований, дыра из GAP закрыта, важное из найденного не пропущено. Не переписывает — выносит замечания с цитатой текста `[A]` и фрагментом источника `[F-id]`.

**Вход.** Артефакт, ТЗ, реестр источников с сырым текстом, список «найдено, но не процитировано» из `scripts/list_unused.py`. Рассуждений и лога автора не получает.

**Выход.** Файл `review-<артефакт>`: замечания [блок] и [замечание], итог, что не проверено.

**Какую дыру закрывает.** Скрипт видит, что цитата есть в источнике, но не видит, что из неё выведено больше, чем она говорит.

**Цена.** Средняя на артефакт: читает источники. Сильная модель.

**Признак провала.** Ноль замечаний на артефакт с пятью и больше выводами без перечня проверенного. Замечания без цитат. Общие слова вместо пунктов.

### nostradamus — новые идеи и лучшая версия

**Место в маршруте.** Не выбирается по приоритетам. Типы «гипотезы», «план проверки», «ТЗ на доработку» — после последнего прохода проверки по сути, до итоговой позиции консультанта и планировщика. Тип «исследование» — после проверки достаточности, до сборщика отчёта. Один раз, вне бюджета шагов тира: правило «мало данных — не ответ» не экономится. Остановка по лимиту или двум промахам — всё равно вызывается перед сдачей. Не вызывается в типах «разбор», «валидация», «вердикты по проверке» и при остановке из-за расхождения с ТЗ.

**Что делает.** Придумывает 5–10 новых идей вне колеи маршрута — другие оси, момент, канал, аудитория, ход наперекор убеждению команды, попутное из материалов, синтетика, чужой опыт; у каждой — почему может сработать, чем отличается от проверенного, что её уточнит, первый шаг на этой неделе и на чём он делается (поле, которое реально есть в источнике, или новый сбор), что её убьёт. Сверяет рамку: в той ли форме ответ на вопрос человека; если нет — черновик нужной формы из новых идей. По каждому ключевому пункту GAP и по GAP 1 — лучшая версия с пометкой «оценка», альтернативы, что различит, следующий шаг. В веб не ходит, вердиктов не меняет, проверенные направления не ранжирует и не перекладывает.

**Вход.** Обязательно — ТЗ, `00k-knowledge.md`, `sources.csv` с сырым текстом, список «Уже проверено» (ось и вердикт каждой гипотезы одной строкой), запросы данных D-N из лога. Желательно — синтетика, `src-*`. Самих гипотез и вердиктов не получает: иначе перекладывает старое.

**Выход.** Файл `02f-forecast.md`: НОВЫЕ ИДЕИ, РАМКА, раздел на каждый ключевой пункт GAP. Проверка формы — `check_forecast.py`, цитаты — `check_step.py`. Проверки смысла нет: это оценка, и она помечена как оценка.

**Какую дыру закрывает.** Проверка честно сужает, но не собирает: все вердикты «сузить» или отчёт «данных не хватает» — и человек остаётся без ответа и без следующего шага.

**Не опора.** `02f-forecast.md` не служит основанием ни одного вывода: ни в проверке по сути, ни в отчёте, ни в следующей задаче. В `context/` не переносится. Консультант и сдача берут версии как версии — с пометкой «оценка».

**Цена.** Средняя. Сильная модель.

**Признак провала.** Новые идеи — пересказ или уточнение проверенных гипотез; схема рамки собрана из старых гипотез. «Нет данных» или «нужно исследование» вместо лучшей версии. Альтернатива — соломенное чучело или пересказ главной версии. Следующий шаг требует аналитика или чужого разрешения. Рамка объявлена совпавшей, когда вопрос «как устроить», а построены разрозненные пары. Оценка подана как факт.

## Цепочка

Консультант — обязательный первый шаг. Основной порядок: консультант → генератор → проверка по сути → Нострадамус → отсев идей → планировщик. Дальше оркестратор выбирает по приоритетам.

### context-reader — разбор материалов

**Место в маршруте.** Шаг 0: сразу после согласования ТЗ, до консультанта, один раз. Если в контексте сырые транскрипты без разборов — после пачки разборов интервью и сводки. В лимит шагов тира не входит.

**Что делает.** Читает весь контекст целиком и по каждому пункту GAP собирает: что уже известно — дословно со ссылками, все относящиеся фрагменты, а не лучшие; утверждения команды с пометкой «проверяется»; противоречия между файлами; чего нет. Плюс таблица покрытия — строка на каждый файл контекста — и до пяти фрагментов «сверх ТЗ», которые могут поменять постановку. Выводов не делает, в сеть не ходит.

**Вход.** Обязательно — ТЗ, реестр источников с сырым текстом файлов контекста. Желательно — разборы интервью и сводка.

**Выход.** Файл `00k-knowledge.md`. Проверка — `check_knowledge.py` и `check_quotes.py`.

**Какую дыру закрывает.** Путь строится по пересказу ТЗ, а не по тому, что уже лежит в материалах: ответы в папке пропускаются, противоречия всплывают в конце.

**Когда не вызывать.** Контекст пустой. Тип выхода «вердикты по проверке».

**Цена.** Средняя-высокая: читает всё. Сильная модель.

**Признак провала.** Файл контекста пропущен в таблице покрытия. По пункту GAP один-два фрагмента при большем числе относящихся. «Чего нет» пусто или общими словами. Вывод или рекомендация вместо фрагмента. Утверждение команды подано как факт. Противоречие сглажено.

### b2b-consultant — оценщик ТЗ

**Место в маршруте.** Первый исполнитель после разбора материалов. Оркестратор начинает выбирать только после его разбора. Консультант входит в бюджет шагов из ТЗ.

**Что делает.** Оценивает ТЗ: в чём реальная ставка, самое рискованное допущение, рыночный контекст, слабые места. Если в ТЗ готовое решение — разбирает решение. Если только проблема или метрика — разбирает постановку.

**Вход.** Согласованное ТЗ с полем РЕШЕНИЕ и карта знания `00k-knowledge.md`. Файлы контекста — по ссылкам из карты, когда нужен фрагмент целиком.

**Выход.** Четыре части:
- слабые места — уходят в GAP генератора
- вектор — одно-два направления, куда двигаться, без конкретных решений и механизмов; задаёт генератору поле поиска
- самое рискованное допущение — источник слоя риска в приоритетах оркестратора
- вопрос, который проверить первым
- путь от AS-IS к TO-BE — 3–5 пунктов «что должно стать известно»: какие пункты GAP закрывает, какие варианты решения сдвигает, чего не хватает в карте знания, зачем, что будет ответом, что перевернёт вектор; один пункт — `[проверка допущения]`; что карта уже отвечает, в путь не идёт; без методов — маршрут строит оркестратор. Каждый пункт GAP — в пути или в строке «Вне пути» с причиной. В валидации путь — вся карта утверждений

Конкретные изменения и альтернативную версию решения не пишет: это работа генератора. Файл `01-review.md`.

**Какую дыру закрывает.** Не проверено, верна ли сама постановка задачи и где в ней главный риск.

**Когда не вызывать.** Не применимо — вызывается всегда, один раз.

**Цена.** Средняя. Веб не обязателен.

**Признак провала.** Не названо ни одного конкретного слабого места. Слабые места сформулированы категориями («нужна сегментация»), а не разрывами в логике. Нет рискованного допущения — слой риска остаётся без источника. В пути названы методы и скиллы вместо того, что узнать; больше пяти пунктов; нет пункта на опровержение своего допущения.

**Сигнал для оркестратора.** Разбор показывает, что ТЗ ставит не ту задачу, — расхождение с ТЗ: остановка и вопрос человеку. Это самая ранняя точка, где ошибка в ТЗ может всплыть.

**Карта утверждений — в типе «валидация».** В первом разборе, кроме четырёх частей, — 5–8 утверждений «что должно быть правдой, чтобы идея сработала» (У-1…У-n) с пометкой ключевых; гипотезы человека входят в карту. Признак провала — утверждения-категории («клиентам нужно»), а не проверяемые факты; идея человека не разложена целиком.

**Режим «итоговая позиция».** Второй вызов, в конце маршрута типов «гипотезы» и «ТЗ на доработку» — после последнего прохода проверки по сути. Вход — ТЗ, гипотезы, итоговые вердикты, из `02f-forecast.md` — рамка и лучшие версии, без своего первого разбора `01-review.md`, чтобы не закреплять собственный вектор. Новые идеи Нострадамуса консультант не ранжирует: они кандидаты в следующий раунд и идут в сдачу отдельным блоком. Выход — `02e-position.md`, до 450 слов, простым языком (`check_readable.py`): первым блоком «что запускать» — кому, что говорим, где, как поймём, что сработало; затем все направления по порядку — ставка, уверенность по числу независимых опор, почему выше следующего, что убьёт, что перевернёт порядок; с чего начать, во что не верит, где расходится с вердиктами. Вердикты не меняет, в веб не ходит. Сильная модель, один шаг бюджета, без проверки смысла. Признак провала — направления «на равных» или «всё зависит от данных» без ставки; позиция пересказывает вердикты, а не ранжирует; уверенность выше, чем позволяет число опор; нет блока «что запускать»; номера гипотез, id или слова системы в тексте.

### hypothesis-generator

**Что делает.** Превращает слабые места и GAP в 3–5 проверяемых гипотез с механизмом.

**Вход.** Обязательно — GAP: из разбора консультанта или из ТЗ. Желательно — вектор консультанта и данные о носителе.

**Режимы.** Генерация с нуля; «ширина» — по строке РЕЖИМ в ТЗ: первый вызов — длинный список `02-long-list.md` на 15–25 ходов (ход, кому, вариант решения, опора, дешёвая проверка, дней до сигнала), отсев — `check_long_list.py` по правилам, известным заранее, второй вызов — гипотезы по 3–5 ходам «в глубину»; «только гигиена» — для гипотез человека в типе «ТЗ на доработку»; «усиление по вердиктам» — после проверки по сути в валидации; переформулировка по результатам живой проверки.

**Выход.** Гипотезы со слотами (субъект, изменение, эффект, механизм) и метками рамок; результат гигиены A/B; блок причины для непрошедших. Если был вектор — одна гипотеза из 3–5 контрольная, вне вектора. У прошедших гигиену — метки опоры: вес опоры и выводимость. Файл `02-hypotheses.md`.

**Какую дыру закрывает.** Понятно, что не так, но непонятно, что с этим делать.

**Когда не вызывать.** Нет ни разбора, ни данных о носителе — сначала источник. Решение уже выбрано и нужен план — это планировщик. Повторно на том же GAP.

**Цена.** Средняя. Без веба.

**Признак провала.** Ни одна гипотеза не прошла гигиену. Четыре из пяти под одной рамкой — разброса не случилось. В режиме ширины — строк не 15–25, прошло отсев меньше трёх, ходы — пересказ слабых мест, а не действия.

**Сигнал для оркестратора.** Контрольная гипотеза сильнее остальных — вектор консультанта, вероятно, выбран неверно. Это расхождение с ТЗ: остановка и вопрос человеку.

### hypothesis-validator

**Что делает.** Проверяет гипотезы по сути: по инструментам методологии через указатель и обязательной сверкой с вебом. Гипотез не придумывает и не переписывает. Отдельно от генератора намеренно — кто строит, тот не проверяет.

**Вход.** Гипотезы от генератора с метками опоры, ТЗ, контекст, `tools-index.md`.

**Режим «отсев идей».** После Нострадамуса, вне бюджета, отдельный контекст: по каждой новой идее — убивает ли её материал, какие возражения её ослабляют (отдельным полем), новая ли она, различает ли первый шаг и выполним ли он на указанном источнике, не след ли одного источника. Вердикт — кажется валидной / переделать первый шаг / снять; данные для следующего раунда. Двух опор не требует: проверка на убийство, а не на доказательство. Файл `02g-ideas-check.md`, проверка формы — `check_ideas.py`. Признак провала — все сняты за «нет опор» или все «валидны» без единого найденного возражения.

**Выход.** Вердикт по каждой гипотезе — держится на бумаге / сузить / не держится — с основанием: какие проверки методологии, какие сверки с вебом, фрагменты источников. Плюс расхождения контекста и веба и дыры, где нужно исследование. Файл `02c-validation.md`.

**Какую дыру закрывает.** Гипотезы построены, но неизвестно, держатся ли они по существу.

**Сверка с вебом — обязательна**, если гипотеза утверждает что-то о внешнем мире, если опоры нет или она слабая, если есть цифра без источника. По `web-protocol.md`: обязательный запрос на опровержение, отбор отчётов, метка уверенности. До двадцати запросов на серию.

**Когда не вызывать.** Гипотез нет или все провалили гигиену. Повторно на тех же гипотезах.

**Цена.** Средняя: веб-сверка, но короткая.

**Признак провала.** Все гипотезы держатся и замечаний нет — проверка слушала то, что хотела услышать.

**Сигналы для оркестратора.** Найденное противоречие проверка классифицирует: против основания ТЗ — стоп; против проверяемой гипотезы или утверждения — штатный вердикт, маршрут идёт; между артефактами системы — не стоп, записывается в лог. Дыра для исследования — кандидат на market-analyze или target-audience-analyst.

### results-reviewer

**Что делает.** Сверяет результаты живой проверки с критериями из плана исходной задачи, проверяет саму проверку на дефекты по M7 и выносит вердикт: подтверждена, переформулировать, отсечена, недостаточно данных.

**Вход.** `03-plan.md` и `02c-validation.md` исходной задачи, результаты от человека.

**Выход.** Вердикты с сигналами, что дальше по каждой гипотезе, блоки к переносу в контекст. Файл `04-results.md` в папке исходной задачи.

**Какую дыру закрывает.** Проверка проведена, но неизвестно, что она показала относительно того, что обещали до неё.

**Место в маршруте.** Только для типа выхода «вердикты по проверке» — первым, вместо консультанта.

**Главное правило.** Критерии не двигаются после результатов.

**Цена.** Низкая.

**Признак провала.** Все гипотезы подтверждены. Вердикт без сигнала. Критерий сдвинут. Дефекты проверки не смотрели.

### project-analyst

**Что делает.** Раскладывает гипотезы или принятое решение в план проверки: задачи, порядок, зависимости, риски.

**Вход.** Гипотезы с вердиктами проверки — «держится на бумаге» и «сузить» (в суженной форме); или принятое решение. «Не держится» в план не идёт. Гипотезы без опоры или с разрывом выводимости ставит первыми — их проверять живыми людьми раньше остальных.

**Выход.** По каждой гипотезе — карточка из M4: метод проверки из M7, выборка, срок, критерий успеха в числах, критерий отсечения, с пометкой «записаны до проверки». Плюс порядок, зависимости, риски. Файл `03-plan.md`.

**Какую дыру закрывает.** Понятно, что проверять, но непонятно, как и в каком порядке.

**Режим «бэклог тестов».** Финиш типа «гипотезы», после итоговой позиции. Вход — гипотезы с итоговыми вердиктами, `02e-position.md`, запросы данных из лога. Выход — `03-backlog.md`: таблица до 12 строк — №, кому и как найти в данных, что говорим, где и кто, метрика, успех, отсечение, срок и цена, что решит; строки дешёвых замен для запросов данных — с тем, чего замена не покажет. Читает человек: `check_readable.py`. Средняя модель, один шаг бюджета. Признак провала — пустая колонка; критерии без чисел; посыл — номер гипотезы, а не слова клиента; тест по «не держится».

**Когда не вызывать.** Гипотезы не прошли проверку по сути — ни одной «держится на бумаге» или «сузить». Решение ещё под вопросом — нужна оценка, а не план.

**Цена.** Низкая. В типе «валидация» — сильная модель: методы и различение версий там — основной результат.

**Признак провала.** Задачи не привязаны к конкретным гипотезам. У гипотез нет критерия успеха и критерия отсечения.

### test-kit

**Что делает.** По плану проверки собирает материалы для запуска: скрипт интервью по M2 с формулировкой после вопросов о прошлом, вставку в скрипт продавца, тексты микротеста, анкету с вынужденным выбором, — и заготовки результатов под критерии плана.

**Вход.** `03-plan.md`, ТЗ, разбор консультанта, путь клиента, если есть.

**Выход.** `03b-test-kit.md` и заготовки в `tasks/<задача>/results-templates/` — не в `results/`: папка `results/` только для того, что принёс человек.

**Какую дыру закрывает.** План есть, но запустить проверку не с чем.

**Место в маршруте.** После планировщика, когда тип выхода — «план проверки». Финиш маршрута.

**Цена.** Низкая.

**Признак провала.** Формулировка звучит раньше вопросов о прошлом. Вопрос «купили бы вы». Шаблон результатов не совпадает с критериями плана.

## Источники данных

Сюда оркестратор ходит вбок — по выбору, а не по списку GAP: только когда без ответа генератор или проверка по сути будут гадать. Вопрос, критерий ответа и бюджет запросов исполнитель получает в вызове от оркестратора и работает по ним, а не по своему плану. Восемь скиллов закрывают восемь разных дыр — «кто носитель», «что у него внутри», «что общего и что расходится у нескольких носителей», «что снаружи на рынке», «что он выбирает вместо нас», «сколько их, сколько платят и хватит ли на цель», «когда: что запускает поиск и где терпеть уже нельзя», «что показали завершённые эксперименты и мог ли тест это увидеть».

### interview-analyst

**Что делает.** Разбирает транскрипт интервью: квалификация респондента, выводы с силой сигнала, открытые вопросы, следующие шаги.

**Вход.** Транскрипты из контекста проекта. Желательно — продукт или ICP как фильтр интерпретации.

**Выход.** Разбор по блокам 0–4, по файлу на интервью: `src-interview-<n>.md`.

**Отвечает на.** Что конкретный респондент делал, чем решал задачу, что сломалось, кто он и насколько его слова — опора.

**Не отвечает на.** Что общего у всех опрошенных (это сводка), как устроен рынок в целом.

**Достаточный ответ — образец.** Разбор на интервью: квалификация респондента, текущее решение, сигналы с силой и дословными фрагментами. Оркестратор подстраивает его под пункт пути, а не копирует.

**Когда не вызывать.** Транскриптов нет. Они уже разобраны — разбор лежит в папке. Нужна картина шире, чем N разговоров, — это market-analyze.

**Цена.** Низкая на одно интервью, растёт с числом транскриптов. В бюджете шагов вся пачка разборов одной задачи — один шаг; сводка (`interview-synthesis`) — отдельный.

**Признак провала.** Выводы без цитат. Цитата без вопроса, на который отвечал респондент. Респондент квалифицирован как «не из ICP» — данные есть, но не про того носителя.

### interview-synthesis

**Что делает.** Сквозная картина по пачке интервью: матрица «респондент × тема», счёт «k из n» по транскриптам, контрасты между сегментами и типами респондентов, одиночные сильные сигналы, «сказал» отдельно от «делал», расхождения с утверждениями команды.

**Вход.** Обязательно — два и больше разбора `src-interview-*.md` и транскрипты в реестре источников. Желательно — ТЗ с носителем и сегментами, строка ПОЗИЦИЯ.

**Выход.** Блоки 0–6 по формату скилла. Файл `src-interviews.md`.

**Отвечает на.** Что общего у опрошенных и у скольких, где сегменты расходятся, что сказал один, но сильно, где слова расходятся с поведением.

**Не отвечает на.** Долю в базе или на рынке — выборка не рынок; то, о чём в интервью не спрашивали.

**Достаточный ответ — образец.** «k из n» по транскриптам у каждого вывода, расхождения по сегментам, одиночные сильные сигналы отдельно. Оркестратор подстраивает его под пункт пути, а не копирует.

**Когда не вызывать.** Разобрано одно интервью. Сводка уже есть, и новых разборов после неё не появилось.

**Цена.** Средняя: читает все разборы и возвращается к транскриптам за счётом.

**Признак провала.** Все темы «у большинства», без «k из n». Нет ни одного контраста. Нет блока одиночных сигналов — сильное у одного утонуло в общем. Число упоминаний подано как важность. Тема посчитана, хотя её поднимал интервьюер.

### market-analyze

**Что делает.** Разведка инфополя: боли аудитории её словами, интенсивность × незакрытость, кто уже реагирует.

**Вход.** Аудитория, рынок и язык поля, цель исследования — из ТЗ.

**Выход.** Записка: боли с цитатами, приоритизация по интенсивности и незакрытости, таблица игроков. Файл `src-market.md`.

**Отвечает на.** Болит ли это у аудитории, какими словами она это говорит, насколько остро и закрыто ли уже. Те же вопросы иначе: что обсуждают, на что жалуются, какие слова использовать в тексте, о чём спрашивают в чатах и на форумах.

**Линза.** «Что болит» — ход за сырьём до генератора (оркестратор, «Линзы до генератора»).

**Не отвечает на.** Доли и причины ухода именно от нас, размер рынка, кто носитель.

**Достаточный ответ — образец.** 3–7 тем боли, у каждой не меньше двух независимых дословных фрагментов, оценка интенсивности и незакрытости, запрос на опровержение. Оркестратор подстраивает его под пункт пути, а не копирует.

**Когда не вызывать.** Аудитория не определена — сначала target-audience-analyst. Вопрос про внутренние процессы, которых нет в открытом поле.

**Цена.** Высокая: много веб-поиска, долго. Не больше одного вызова на задачу.

**Пауза на плане поиска** в режиме оркестратора снята: план уходит оркестратору в резюме, в лог его пишет оркестратор.

**Признак провала.** Боли без цитат аудитории. Все боли «горячие и незакрытые» — приоритизация ничего не различает.

### target-audience-analyst

**Что делает.** Собирает документ ЦА: профили, барьеры, триггеры переключения, границы для таргетинга. Факты отделены от гипотез.

**Вход.** Обязательно — продукт, решаемая проблема, рынок. Желательно — интервью, аналитика.

**Выход.** Документ из семи разделов. Файл `src-audience.md`.

**Отвечает на.** Кто носитель, какие роли участвуют в выборе, чем различаются сегменты, что держит и что переключает. Те же вопросы иначе: как делить аудиторию, какие группы бывают снаружи, кто решает и кто исполняет, кому писать.

**Линза.** «Кто» — ход за сырьём до генератора.

**Не отвечает на.** Размер сегментов, интенсивность боли на рынке.

**Достаточный ответ — образец.** Профили с ролями — кто платит, кто пользуется, кто решает; у каждого утверждения не меньше двух фрагментов или пометка «гипотеза»; границы для таргетинга. Оркестратор подстраивает его под пункт пути, а не копирует.

**Когда не вызывать.** Носитель уже определён в ТЗ и подтверждён интервью. Нужна боль, а не профиль — это market-analyze.

**Цена.** Средняя-высокая: 3–6 веб-запросов.

**Пауза на плане поиска** в режиме оркестратора снята: план уходит оркестратору в резюме, в лог его пишет оркестратор.

**Признак провала.** Профили общие («малый бизнес») без ролей и точки входа.

### alternatives-analyst

**Что делает.** Карта альтернатив: куда на самом деле уходят клиенты — ничегонеделание, ручной процесс, найм, прямой конкурент, — с весом, дословными причинами и разбором двух главных противников. Изнутри наружу: сначала несвершившиеся сделки и интервью из контекста, потом веб.

**Вход.** ТЗ: носитель, точка слома, сегмент. Желательно — несвершившиеся сделки из CRM, отмены, интервью с блоком «привычка».

**Выход.** Карта альтернатив с весом и дословными причинами; сортировка причин по адресам; разбор двух противников — что перевесило, что не сможет исправить, в чём силён, когда выигрывает у нас, цена и стоимость ухода, вердикт «воюем / наблюдаем / игнорируем»; словарь клиента; какие каналы пройдены и где пусто. Файл `src-alternatives.md`.

**Отвечает на.** Что клиент делает вместо нас, почему выбирает не нас, с кем на деле конкурируем, что противник не сможет исправить. Те же вопросы иначе: как клиент обходится без продукта, кто делает это за него (бухгалтер, подрядчик, второй поставщик), что он делает, чтобы задача не возникла вовсе.

**Линза.** «Вместо нас» — ход за сырьём до генератора.

**Не отвечает на.** Долю альтернатив в нашей базе без выгрузки потерь (это запрос данных), боли рынка в целом.

**Достаточный ответ — образец.** Карта альтернатив по четырём уровням, включая ничегонеделание, с дословными причинами; вес с пометкой «доля» или «оценка»; два противника с вердиктом. Оркестратор подстраивает его под пункт пути, а не копирует.

**Веб — обязателен**, если внутренних данных о потерях нет или их мало. Каналы: отзывы о конкурентах, форумы и профессиональные чаты, истории переходов, поисковые подсказки и похожие вопросы, вакансии, тендеры, сравнительный контент, смежные решения. Каналы дают кандидатов и причины; вес и вердикт — только по модели альтернатив. По `web-protocol.md`. До пятнадцати запросов с данными о потерях, до тридцати — без них. Сайт конкурента — только проверка обещания.

**Когда не вызывать.** Альтернативы уже разобраны в контексте и разбору меньше квартала. Нужны боли рынка, а не альтернативы — это market-analyze.

**Цена.** Средняя-высокая: веб-поиск.

**Признак провала.** В карте только прямые конкуренты, без ничегонеделания и непрямых. Причины — категории, а не слова клиентов. Вес «на ощущение» или по тому, в каком канале нашлось больше. Один источник засчитан как несколько. У противника только слабости.

### customer-path

**Что делает.** Путь клиента по M3: триггеры трёх типов, текущие решения в порядке, в каком их пробуют, точка слома по трём признакам, путь от слома в обе стороны, таблица инсайтов.

**Вход.** ТЗ, контекст проекта: обращения в поддержку, опросы при отмене, записи демо, интервью. Желательно — разбор альтернатив.

**Выход.** Карточки триггеров и точки слома, путь, таблица инсайтов не меньше пяти строк. Файл `src-path.md`.

**Отвечает на.** Что запускает поиск решения, чем пробуют обойтись до нас, в какой момент терпеть уже нельзя, есть ли сезонность. Те же вопросы иначе: когда писать, что происходит до события, как прогревать до триггера, почему одни готовы раньше других, что делает человек в день, когда проблема случилась.

**Линза.** «Когда» — ход за сырьём до генератора. Первая линза для задач про триггеры, прогрев и коммуникацию по событиям.

**Не отвечает на.** Как часто триггер встречается в нашей базе (это запрос данных), почему выбирают конкурента.

**Достаточный ответ — образец.** Триггеры по типам с фрагментами, текущие решения в порядке попыток, точка слома по трём признакам, таблица инсайтов не меньше пяти строк. Оркестратор подстраивает его под пункт пути, а не копирует.

**Сначала внутренние данные, потом веб** по `web-protocol.md`: чаты, форумы, отзывы 2–3★, сезонность запросов, вакансии, тендеры. До двадцати запросов.

**Когда не вызывать.** Путь по этому сегменту уже есть в контексте и ему меньше квартала.

**Цена.** Средняя.

**Признак провала.** Триггер — желание, а не событие. Момент — «в любой момент». Слом без последствий.

### market-sizing

**Что делает.** Оценка рынка: сколько компаний в сегменте, сколько они уже платят за смежное и достижима ли цель из ТЗ. Обратный счёт из M11: цель ÷ чек = нужно клиентов, сверка с числом компаний. Снизу вверх, диапазонами, с метками уверенности.

**Вход.** ТЗ: сегмент, география, цель в цифрах и срок. Желательно — разбор консультанта и внутренние данные из контекста: клиентская база по сегментам, биллинг, воронка с конверсиями.

**Выход.** По каждой нише: число компаний, чек, нужное число клиентов, доля сегмента как явное допущение, вердикт «достижимо / на грани / недостижимо», чувствительность. Файл `src-market-size.md`.

**Отвечает на.** Сколько компаний в сегменте, сколько они уже платят за смежное, достижима ли цель в цифрах.

**Не отвечает на.** Нашу конверсию и чек без своих данных (запрос данных или формула с неизвестными), боли и альтернативы.

**Достаточный ответ — образец.** Диапазон «компании × чек» снизу вверх, числа через реестр, обратный счёт цели, вердикт по нише. Оркестратор подстраивает его под пункт пути, а не копирует.

**Внутренние данные — первыми, если есть**: свой чек, свои клиенты в сегменте, конверсия — вместо допущений. **Веб** — для размера сегмента и расходов на смежное, по `web-protocol.md`: статистика и реестры, отраслевые ассоциации, проверенные отчёты, цены смежных продуктов, тендеры, вакансии как стоимость замещающей альтернативы. До двадцати пяти запросов.

**Когда не вызывать.** В ТЗ нет ни цели в цифрах, ни вопроса о масштабе. Сегмент не определён даже примерно — сначала target-audience-analyst.

**Цена.** Высокая: много веб-поиска.

**Признак провала.** Точечные оценки без диапазонов. Размер сверху вниз из одного отчёта. Доля сегмента без пометки «допущение». Все ниши «достижимы». Внутренние данные были, а расчёт только по открытым.

**Сигнал для оркестратора.** Цель недостижима во всех нишах — это расхождение с ТЗ: остановка и вопрос человеку с обоснованным диапазоном достижимого.

**Две формы обратного счёта.** Оценка рынка — одна из двух допустимых форм. Другая — расчёт внутри плана проверки, когда узкое место не размер рынка, а своя конверсия и чек. Тогда market-sizing не вызывается, а в логе записано, почему.

### experiment-review — разбор завершённых экспериментов

**Что делает.** Берёт готовые отчёты об экспериментах и по каждому считает: что тест мог увидеть при фактических группах (чувствительность), что показал (интервал, знак), какой исход — «эксперимент скомпрометирован», «эффекта нет», «не различимо», «заложенный исключён» — и что общего у исходов по пачке. Проверяет, какое прочтение поля «мощность» подтверждается числами; считает вероятность хотя бы одной значимости на k тестах; отделяет измеренное (доходимость, воронка) от выведенного. Не ищет в вебе.

**Вход.** Отчёты об экспериментах в контексте (зарегистрированные источники); пункт GAP, вопрос и критерий ответа. Желательно — карта знания.

**Выход.** Файл `src-experiments.md`: таблица по тестам, прочтение поля мощности, пачка, расхождения в отчётах, что не посчитано, запросы данных, выводы с метками уверенности. Числа — через реестр чисел.

**Отвечает на.** Мог ли тест увидеть заложенный эффект; какие неудачи значат «эффекта нет», а какие «не различимо»; держится ли единственный положительный результат против числа сравнений; как исход делится по оси «не окупается / эффекта не видно»; где в планах тестов отсутствует запись критериев до запуска.

**Не отвечает на.** Почему клиенты не отреагировали (живая проверка); сколько таких тестов бывает в отрасли (market-analyze, внешний ориентир); как построить следующий тест (project-analyst); сверку результатов с планом из прошлой задачи (results-reviewer).

**Достаточный ответ — образец.** Таблица по каждому тесту с числами из отчёта и производными в реестре чисел, отметка исхода с основанием, выводы по пачке с метками уверенности, запросы данных с дешёвой заменой.

**Когда не вызывать.** В контексте нет отчётов об экспериментах с числами. Вопрос про отдельную гипотезу до проверки (hypothesis-validator). Вопрос про один эксперимент после запуска по плану прошлой задачи (results-reviewer).

**Цена.** Высокая: расчёты, много чисел в реестр. Сильная модель.

**Признак провала.** Поле «мощность» принято по подписи. Все тесты в одном исходе. Единственный успех без поправки на число сравнений. «Итоги не подводили» посчитаны как провал оффера. Число не в реестре. Причина поведения клиентов подана как факт. Имена, ссылки или коды из отчётов в артефакте.

**Сигнал для оркестратора.** Отчёты показывают, что ТЗ спрашивает о «неудачах» в смысле, который по данным не определяется (классы причин совпадают по построению) — исходы «не различимо» и «нет данных» идут в сдачу отдельно.

### synthetic-interviews — старт с чистого листа

**Место в маршруте.** Не выбирается оркестратором. Вызывается только если в ТЗ стоит режим «старт с синтетики» — его предлагает диспетчер при полноте 0–1, решает человек на согласовании. Тогда — сразу после консультанта.

**Второй режим — «пробный прогон».** Вызывается по строке РЕЖИМ «пробный прогон: да» (ответ человека на четвёртый вопрос диспетчера), после набора для проверки: прогоняет скрипт живой проверки по 3–5 синтетическим персонам и ищет наводящие вопросы, двусмысленности, эхо и пропущенные ветки. Файл `03c-rehearsal.md`; правки к скрипту предлагаются списком «было → стало → почему», последний раздел — «СЛЕДСТВИЯ»: статус каждого теста (как есть / после правки / не запускать), что меняется в решении, что подсказали персоны. Сам ничего не применяет: следствия для эксперимента применяет автор бэклога или плана в режиме исправления по пробному прогону. Всё помечено `[синтетика]`: о клиентах свидетельством не является, о дефектах инструмента — является. Бюджет — плюс один шаг; исправление по нему — вне бюджета.

**Что делает.** Интервью с синтетическими представителями потенциальной аудитории, чтобы было от чего оттолкнуться, когда данных о носителе нет совсем.

**Вход.** Описание предполагаемой аудитории и проблемы из ТЗ, разбор консультанта.

**Выход.** Стартовый материал о носителе: как он может описывать задачу, текущее решение, возражения. Каждый фрагмент помечен `[синтетика]`. Файл `src-synthetic.md`.

**Главное правило.** Синтетика никогда не засчитывается как опора. С синтетическим респондентом ничего не случалось — правило свидетельства её не пропускает. Гипотезы, выросшие из синтетики, получают метку «опоры нет» и идут в план первыми — на проверку живыми людьми. Синтетика ломает чистый лист, но ничего не подтверждает.

**Не закрывает никогда** дыры о фактах рынка: размер, число компаний, бюджеты, цены, конкуренты. Пустой контекст проекта — не повод для синтетики: факты ищутся в сети.

**Цена.** Средняя.

**Признак провала.** Все синтетические респонденты согласны с исходной идеей — это эхо, а не материал.

## Приоритеты

Порядок закрытия дыр из GAP — тремя слоями, как у менеджера проекта.

1. **Зависимости — жёсткий фильтр.** Дыра блокирующая, если без неё у следующего нужного скилла нет обязательного входа (поле «Вход — обязательно»). Блокирующие закрываются первыми, независимо от важности.
2. **Риск.** Среди незаблокированных первой идёт дыра, связанная с самым рискованным допущением из разбора консультанта.
3. **Стоимость — тай-брейк.** При равном риске сначала дешёвый скилл (поле «Цена»).

В логе каждое решение объясняется по слою, который его определил: «закрываю X, потому что оно блокирует Y», «потому что за ним главное допущение», «потому что дешевле».

## Готовность

Диспетчер выбирает в ТЗ один из семи типов выхода. Тип задаёт точку финиша маршрута.

| Тип выхода | Когда | Финиш |
| --- | --- | --- |
| Разбор | нужна только оценка | после консультанта |
| Гипотезы | нужно понять, что делать | после проверки по сути и итоговой позиции |
| План проверки | нужно довести до действий | после набора для проверки |
| Вердикты по проверке | принесли результаты живой проверки | после сверки, или после проверки по сути, если были переформулировки |
| Валидация | человек принёс свою идею или гипотезы: что не так, где слабо, как усилить, как проверить | после документа `06-validation.md` и его проверки смысла |
| Исследование | нужно понять, что известно, без выбора решения | после отчёта `06-research.md` и его проверки смысла |
| ТЗ на доработку | оценить идеи или гипотезы и наполнить конкретикой: ТЗ аналитику и бриф редактору | после писателя брифа, файлы `07a-analyst.md`, `07b-editor.md`, `07c-decisions.md` |

Готовность проверяется механически: типовой чек-лист плюс условие из ТЗ, если оно есть. Модель не оценивает, «хорошо ли получилось», — только сверяет пункты.

### Типовые чек-листы

**Разбор**
- названо хотя бы одно слабое место как разрыв логики, а не категория
- есть самое рискованное допущение
- есть вектор: одно-два направления без конкретных решений
- есть вопрос, который проверить первым

**Гипотезы**
- перед генератором в логе блок ЛИНЗЫ: по каждой из четырёх линз «зову» или «не нужно» с допустимой причиной; при ВЕБ: да хотя бы одно «зову» (`check_log_sources.py`)
- не меньше трёх прошли гигиену A и B
- у каждой есть опровергающее наблюдение
- каждая привязана к пункту GAP
- не больше половины под одной рамкой
- если был вектор — есть контрольная гипотеза
- у каждой гипотезы есть вердикт проверки по сути с основанием
- хотя бы одна гипотеза сужена или получила замечание — или объяснено, почему нет
- есть `02g-ideas-check.md`, `check_ideas.py` без ошибок: вердикт отсева по каждой новой идее, у живых — данные для следующего раунда; в сдаче блок «А ещё есть идеи»
- есть `02f-forecast.md`, `check_forecast.py` без ошибок: не меньше пяти новых идей с «не повторяет», «уточнит» и первым шагом; рамка сверена; по каждому ключевому пункту GAP — лучшая версия, альтернатива, что различит, следующий шаг
- есть `02e-position.md`: что запускать, все направления по порядку, с чего начать, во что не верим; `check_readable.py` без ошибок
- есть `03-backlog.md`: у каждого теста заполнены все колонки, критерии успеха и отсечения в числах; `check_readable.py` без ошибок
- если в РЕЖИМЕ «пробный прогон: да» — есть `03c-rehearsal.md` с разделом «СЛЕДСТВИЯ», в `03-backlog.md` блок «ПО ПРОБНОМУ ПРОГОНУ» с ответом на каждое следствие; `check_rehearsal.py` без ошибок; «что запускать» в сдаче не ведёт на тест со статусом «не запускать»
- в режиме ширины — `check_long_list.py` без ошибок, ходы «в запасе» в сдаче словами

**План проверки**
- каждая задача привязана к конкретной гипотезе
- у каждой гипотезы есть метод проверки, критерий успеха и критерий отсечения
- порядок проверки объяснён через зависимости или риск
- риски названы
- есть `02g-ideas-check.md`, `check_ideas.py` без ошибок: вердикт отсева по каждой новой идее, у живых — данные для следующего раунда; в сдаче блок «А ещё есть идеи»
- есть `02f-forecast.md`, `check_forecast.py` без ошибок
- если в РЕЖИМЕ «пробный прогон: да» — есть `03c-rehearsal.md`, все ответы персон помечены `[синтетика]`, правки к скрипту оформлены списком «было → стало → почему»; `check_rehearsal.py` без ошибок: у каждого теста статус, в плане блок «ПО ПРОБНОМУ ПРОГОНУ» с ответом на каждое следствие
- есть набор для проверки: материалы под метод каждой гипотезы и заготовки результатов, поля которых совпадают с критериями плана
- если в TO-BE цель в цифрах — есть обратный счёт в одной из двух форм: оценка рынка или формула цели с неизвестными и проверками, которые их заполнят

**Вердикты по проверке**
- у каждой гипотезы из плана есть вердикт — включая «недостаточно данных»
- каждый вердикт стоит на сигнале: числа или дословная реакция
- критерии взяты из плана без изменений
- дефекты проверки проверены по M7
- для «переформулировать» — если был генератор, новые гипотезы опираются на результаты

**Валидация**
- в первом разборе есть карта утверждений: 5–8 проверяемых утверждений, ключевые отмечены; идея и гипотезы человека разложены целиком
- у каждого утверждения в `06-validation.md` исход — подтверждается / опровергается / нет данных — с числом независимых источников и с «за» и «против» дословно; если «против» нет — сказано, где искали
- по каждому ключевому утверждению материал из двух типов каналов или записано, почему второго нет
- раздел «что не так»: разрывы логики и противоречия, каждое — с опорой
- у каждого слабого места — усиление: было → стало → почему, из какого исхода следует; новых идей вместо идеи человека нет
- у каждого утверждения с исходом «нет данных» и у каждой усиленной версии — метод проверки с выборкой, сроком, метрикой и критериями успеха и отсечения, записанными до проверки
- блок «СЧЁТ ОПОР» совпадает с `checks/trust.md` дословно; есть «проверить вручную» и «не искали и не нашли»
- запросы данных D-N вынесены в сдачу блоком «Запросы данных»

**Исследование**
- у каждого пункта GAP есть исход в отчёте: ответ, ответ с оговоркой, стороны или не закрыто — без пропусков
- у каждого пункта `[ключевой]` ответ с уверенностью не ниже средней, или он первой строкой в «проверить вручную» с причиной и с лучшей версией и следующим шагом из `02f-forecast.md`
- есть `02g-ideas-check.md`, `check_ideas.py` без ошибок: вердикт отсева по каждой новой идее, у живых — данные для следующего раунда; в сдаче блок «А ещё есть идеи»
- есть `02f-forecast.md`, `check_forecast.py` без ошибок
- позиция занята только там, где исход «ответ»
- у каждого ответа есть контраргумент или сказано, почему его нет
- блок «СЧЁТ ОПОР» в отчёте совпадает с `checks/trust.md` дословно (`check_artifact --contains`)
- числа в выводах — только `[N-id]` из реестра; `check_numbers` без ошибок

### Условие из ТЗ

Диспетчер может добавить своё условие готовности, только в наблюдаемой форме: должно быть понятно, какой факт в результате его подтверждает. По тому же правилу, что фальсифицируемость в гигиене.

- «гипотезы должны быть сильными» — не принимается
- «у каждой гипотезы метод проверки не требует разработки» — принимается

Условие видно человеку при согласовании ТЗ.

## Сдача

**Успешный финиш.** Результат плюс короткая сдача в `08-handoff.md` — часть для человека простым языком, под заголовком «## Служебное» всё остальное; в конце блок «Перенесено в контекст». В части для человека, если был Нострадамус, — блок «Лучшая версия и следующий шаг»: по каждому ключевому вопросу версия словами с пометкой «оценка», что её различит и что сделать на этой неделе; черновик рамки, если она не совпала. Последним в части для человека — блок «А ещё есть идеи» — после оценки текущих гипотез: идеи Нострадамуса с вердиктом отсева «кажется валидной» или «переделать первый шаг», каждая — суть, почему кажется валидной, каких данных понадобится для следующего раунда, первый шаг на этой неделе; снятые — одной строкой с причиной. Это не ставки, а кандидаты в следующий раунд: их берёт диспетчер, когда человек продолжит.
- чек-лист готовности по пунктам со статусом каждого
- маршрут — одна строка на шаг: какой скилл и по какому слою приоритета выбран
- что осталось незакрытым в GAP
- запросы данных: все блоки D-N из лога — вопрос, что снять, разрезы, зачем, дешёвая замена, если данных не будет; человек отдаёт их аналитику
- числа: сколько фактов, производных, допущений; допущения перечислены
- смысл: по каждому проверенному артефакту — блокирующих N, исправлено, снято, оспорено; оспоренные — с причиной автора, решает человек
- опоры: строка из `checks/quotes.md` — сколько источников, сколько независимых корней, сколько прочитано не целиком, сколько цитат не прошло и что с ними сделано

**Остановка по правилу** — лимит шагов, два промаха подряд или финальный чек-лист не сошёлся. То же самое плюс причина остановки.

**Замечания к системе** — последний блок любой сдачи: что оркестратор заметил про скиллы и реестр по ходу. Правки скиллов посреди задачи не делаются и не предлагаются.

**Продолжение — только через ТЗ.** Диспетчер пересобирает ТЗ с учётом того, что выяснилось: сузить задачу, сменить тип выхода, поправить условие готовности. Человек согласует — маршрут продолжается с места остановки с новым бюджетом. Продолжения «ещё на пару шагов» без правки ТЗ нет: остановка почти всегда значит, что ТЗ было слишком широким или ожидание неверным.

**Перенос в контекст проекта** — автоматически, в конце маршрута. В контекст переходят только материалы источников (`src-*`) и результаты живой проверки из `04-results.md`, в `context/from-tasks/`, с шапкой: какой скилл, какая задача, дата, тип материала, и строкой «материал системы: опора — только приведённые в нём фрагменты исходных источников; блоки “Оценка.” опорой не бывают». Текст гипотез, вердикты кабинетной проверки, планы и синтетика не переходят никогда.
