# Реестр скиллов оркестратора

Оркестратор читает этот файл один раз в начале задачи и выбирает по нему. Главное поле — «какую дыру закрывает»: по нему GAP из ТЗ сопоставляется со скиллами.

Все, кто ходит в веб, работают по `web-protocol.md`: уровни источников, отбор отчётов, запрос на опровержение, триангуляция, метки уверенности.

Свой артефакт скилл пишет сам — ровно в путь, который передал оркестратор; имя файла — из поля «Выход» ниже. Больше ничего не создаёт и не правит: ни `log.md`, ни чужие файлы, ни имена. Оркестратору возвращает путь, короткое резюме и сигналы. Лог ведёт только оркестратор.

**Режим оркестратора.** После согласования ТЗ маршрут идёт без пауз. Скилл в режиме оркестратора не завершает ответ: отдаёт результат и возвращает управление оркестратору. Ответ человеку заканчивается только сдачей, остановкой по правилу или вопросом о втором возврате. Скиллы, которые в ручном режиме останавливаются на согласование плана поиска (market-analyze, target-audience-analyst), здесь строят план, возвращают его оркестратору в резюме и сразу ищут. В лог план записывает оркестратор.

## Цепочка

Консультант — обязательный первый шаг. Основной порядок: консультант → генератор → проверка по сути → планировщик. Дальше оркестратор выбирает по приоритетам.

### b2b-consultant — оценщик ТЗ

**Место в маршруте.** Всегда первый шаг после согласования ТЗ. Оркестратор начинает выбирать только после его разбора. Консультант входит в бюджет шагов из ТЗ.

**Что делает.** Оценивает ТЗ: в чём реальная ставка, самое рискованное допущение, рыночный контекст, слабые места. Если в ТЗ готовое решение — разбирает решение. Если только проблема или метрика — разбирает постановку.

**Вход.** Согласованное ТЗ. Желательно — контекст проекта.

**Выход.** Четыре части:
- слабые места — уходят в GAP генератора
- вектор — одно-два направления, куда двигаться, без конкретных решений и механизмов; задаёт генератору поле поиска
- самое рискованное допущение — источник слоя риска в приоритетах оркестратора
- вопрос, который проверить первым

Конкретные изменения и альтернативную версию решения не пишет: это работа генератора. Файл `01-review.md`.

**Какую дыру закрывает.** Не проверено, верна ли сама постановка задачи и где в ней главный риск.

**Когда не вызывать.** Не применимо — вызывается всегда, один раз.

**Цена.** Средняя. Веб не обязателен.

**Признак провала.** Не названо ни одного конкретного слабого места. Слабые места сформулированы категориями («нужна сегментация»), а не разрывами в логике. Нет рискованного допущения — слой риска остаётся без источника.

**Сигнал для оркестратора.** Разбор показывает, что ТЗ ставит не ту задачу, — расхождение с ТЗ: остановка и вопрос человеку. Это самая ранняя точка, где ошибка в ТЗ может всплыть.

### hypothesis-generator

**Что делает.** Превращает слабые места и GAP в 3–5 проверяемых гипотез с механизмом.

**Вход.** Обязательно — GAP: из разбора консультанта или из ТЗ. Желательно — вектор консультанта и данные о носителе.

**Режимы.** Генерация с нуля; «только гигиена» — для гипотез человека в аудите; «усиление по вердиктам» — после проверки по сути в аудите; переформулировка по результатам живой проверки.

**Выход.** Гипотезы со слотами (субъект, изменение, эффект, механизм) и метками рамок; результат гигиены A/B; блок причины для непрошедших. Если был вектор — одна гипотеза из 3–5 контрольная, вне вектора. У прошедших гигиену — метки опоры: вес опоры и выводимость. Файл `02-hypotheses.md`.

**Какую дыру закрывает.** Понятно, что не так, но непонятно, что с этим делать.

**Когда не вызывать.** Нет ни разбора, ни данных о носителе — сначала источник. Решение уже выбрано и нужен план — это планировщик. Повторно на том же GAP.

**Цена.** Средняя. Без веба.

**Признак провала.** Ни одна гипотеза не прошла гигиену. Четыре из пяти под одной рамкой — разброса не случилось.

**Сигнал для оркестратора.** Контрольная гипотеза сильнее остальных — вектор консультанта, вероятно, выбран неверно. Это расхождение с ТЗ: остановка и вопрос человеку.

### hypothesis-validator

**Что делает.** Проверяет гипотезы по сути: по инструментам курса через указатель и обязательной сверкой с вебом. Гипотез не придумывает и не переписывает. Отдельно от генератора намеренно — кто строит, тот не проверяет.

**Вход.** Гипотезы от генератора с метками опоры, ТЗ, контекст, `course-index.md`.

**Выход.** Вердикт по каждой гипотезе — держится на бумаге / сузить / не держится — с основанием: какие проверки курса, какие сверки с вебом, фрагменты источников. Плюс расхождения контекста и веба и дыры, где нужно исследование. Файл `02c-validation.md`.

**Какую дыру закрывает.** Гипотезы построены, но неизвестно, держатся ли они по существу.

**Сверка с вебом — обязательна**, если гипотеза утверждает что-то о внешнем мире, если опоры нет или она слабая, если есть цифра без источника. По `web-protocol.md`: обязательный запрос на опровержение, отбор отчётов, метка уверенности. До двадцати запросов на серию.

**Когда не вызывать.** Гипотез нет или все провалили гигиену. Повторно на тех же гипотезах.

**Цена.** Средняя: веб-сверка, но короткая.

**Признак провала.** Все гипотезы держатся и замечаний нет — проверка слушала то, что хотела услышать.

**Сигналы для оркестратора.** Найденное противоречие проверка классифицирует: против основания ТЗ — стоп; против проверяемой гипотезы или утверждения — штатный вердикт, маршрут идёт; между артефактами системы — не стоп, записывается в лог. Дыра для исследования — кандидат на market-analyze или target-audience-analyst.

### results-reviewer

**Что делает.** Сверяет результаты живой проверки с критериями из плана исходной задачи, проверяет саму проверку на дефекты по M7 и выносит вердикт: подтверждена, переформулировать, отсечена, недостаточно данных.

**Вход.** `03-plan.md` и `02c-validation.md` исходной задачи, результаты от человека.

**Выход.** Вердикты с сигналами, что дальше по каждой гипотезе, блоки к переносу в контекст. Файл `04-results.md` в папке исходной задачи.

**Какую дыру закрывает.** Проверка проведена, но неизвестно, что она показала относительно того, что обещали до неё.

**Место в маршруте.** Только для типа выхода «вердикты по проверке» — первым, вместо консультанта.

**Главное правило.** Критерии не двигаются после результатов.

**Цена.** Низкая.

**Признак провала.** Все гипотезы подтверждены. Вердикт без сигнала. Критерий сдвинут. Дефекты проверки не смотрели.

### project-analyst

**Что делает.** Раскладывает гипотезы или принятое решение в план проверки: задачи, порядок, зависимости, риски.

**Вход.** Гипотезы с вердиктами проверки — «держится на бумаге» и «сузить» (в суженной форме); или принятое решение. «Не держится» в план не идёт. Гипотезы без опоры или с разрывом выводимости ставит первыми — их проверять живыми людьми раньше остальных.

**Выход.** По каждой гипотезе — карточка из M4: метод проверки из M7, выборка, срок, критерий успеха в числах, критерий отсечения, с пометкой «записаны до проверки». Плюс порядок, зависимости, риски. Файл `03-plan.md`.

**Какую дыру закрывает.** Понятно, что проверять, но непонятно, как и в каком порядке.

**Когда не вызывать.** Гипотезы не прошли проверку по сути — ни одной «держится на бумаге» или «сузить». Решение ещё под вопросом — нужна оценка, а не план.

**Цена.** Низкая.

**Признак провала.** Задачи не привязаны к конкретным гипотезам. У гипотез нет критерия успеха и критерия отсечения.

### test-kit

**Что делает.** По плану проверки собирает материалы для запуска: скрипт интервью по M2 с формулировкой после вопросов о прошлом, вставку в скрипт продавца, тексты микротеста, анкету с вынужденным выбором, — и заготовки результатов под критерии плана.

**Вход.** `03-plan.md`, ТЗ, разбор консультанта, путь клиента, если есть.

**Выход.** `03b-test-kit.md` и заготовки в `tasks/<задача>/results-templates/` — не в `results/`: папка `results/` только для того, что принёс человек.

**Какую дыру закрывает.** План есть, но запустить проверку не с чем.

**Место в маршруте.** После планировщика, когда тип выхода — «план проверки». Финиш маршрута.

**Цена.** Низкая.

**Признак провала.** Формулировка звучит раньше вопросов о прошлом. Вопрос «купили бы вы». Шаблон результатов не совпадает с критериями плана.

## Источники данных

Сюда оркестратор ходит вбок, когда дыру из GAP нечем закрыть без данных. Шесть скиллов закрывают шесть разных дыр — «кто носитель», «что у него внутри», «что снаружи на рынке», «что он выбирает вместо нас», «сколько их, сколько платят и хватит ли на цель», «когда: что запускает поиск и где терпеть уже нельзя».

### interview-analyst

**Что делает.** Разбирает транскрипт интервью: квалификация респондента, выводы с силой сигнала, открытые вопросы, следующие шаги.

**Вход.** Транскрипты из контекста проекта. Желательно — продукт или ICP как фильтр интерпретации.

**Выход.** Разбор по блокам 0–4, по файлу на интервью: `src-interview-<n>.md`.

**Какую дыру закрывает.** В контексте есть сырые интервью, но из них не вытащена структура: не видно носителя, его текущего решения, опоры под механизм.

**Когда не вызывать.** Транскриптов нет. Они уже разобраны — разбор лежит в папке. Нужна картина шире, чем N разговоров, — это market-analyze.

**Цена.** Низкая на одно интервью, растёт с числом транскриптов.

**Признак провала.** Выводы без цитат. Респондент квалифицирован как «не из ICP» — данные есть, но не про того носителя.

### market-analyze

**Что делает.** Разведка инфополя: боли аудитории её словами, интенсивность × незакрытость, кто уже реагирует.

**Вход.** Аудитория, рынок и язык поля, цель исследования — из ТЗ.

**Выход.** Записка: боли с цитатами, приоритизация по интенсивности и незакрытости, таблица игроков. Файл `src-market.md`.

**Какую дыру закрывает.** Неизвестно, болит ли это у рынка и кто уже закрывает эту боль — собственных данных недостаточно.

**Когда не вызывать.** Аудитория не определена — сначала target-audience-analyst. Вопрос про внутренние процессы, которых нет в открытом поле.

**Цена.** Высокая: много веб-поиска, долго. Не больше одного вызова на задачу.

**Пауза на плане поиска** в режиме оркестратора снята: план уходит оркестратору в резюме, в лог его пишет оркестратор.

**Признак провала.** Боли без цитат аудитории. Все боли «горячие и незакрытые» — приоритизация ничего не различает.

### target-audience-analyst

**Что делает.** Собирает документ ЦА: профили, барьеры, триггеры переключения, границы для таргетинга. Факты отделены от гипотез.

**Вход.** Обязательно — продукт, решаемая проблема, рынок. Желательно — интервью, аналитика.

**Выход.** Документ из семи разделов. Файл `src-audience.md`.

**Какую дыру закрывает.** Неясно, кто носитель: сегменты, роли, барьеры. Субъект гипотез размыт.

**Когда не вызывать.** Носитель уже определён в ТЗ и подтверждён интервью. Нужна боль, а не профиль — это market-analyze.

**Цена.** Средняя-высокая: 3–6 веб-запросов.

**Пауза на плане поиска** в режиме оркестратора снята: план уходит оркестратору в резюме, в лог его пишет оркестратор.

**Признак провала.** Профили общие («малый бизнес») без ролей и точки входа.

### alternatives-analyst

**Что делает.** Карта альтернатив: куда на самом деле уходят клиенты — ничегонеделание, ручной процесс, найм, прямой конкурент, — с весом, дословными причинами и разбором двух главных противников. Изнутри наружу: сначала несвершившиеся сделки и интервью из контекста, потом веб.

**Вход.** ТЗ: носитель, точка слома, сегмент. Желательно — несвершившиеся сделки из CRM, отмены, интервью с блоком «привычка».

**Выход.** Карта альтернатив с весом и дословными причинами; сортировка причин по адресам; разбор двух противников — что перевесило, что не сможет исправить, вердикт «воюем / наблюдаем / игнорируем». Файл `src-alternatives.md`.

**Какую дыру закрывает.** Неизвестно, против чего на самом деле идёт борьба: что клиент делает вместо нас и почему.

**Веб — обязателен**, если внутренних данных о потерях нет или их мало: отзывы 2–3★ свои и конкурентов, профессиональные чаты, форумы, вакансии, тендеры, поисковые запросы. По `web-protocol.md`. До пятнадцати запросов с данными о потерях, до тридцати — без них. Сайт конкурента — только проверка обещания.

**Когда не вызывать.** Альтернативы уже разобраны в контексте и разбору меньше квартала. Нужны боли рынка, а не альтернативы — это market-analyze.

**Цена.** Средняя-высокая: веб-поиск.

**Признак провала.** В карте только прямые конкуренты, без ничегонеделания и непрямых. Причины — категории, а не слова клиентов. Вес «на ощущение».

### customer-path

**Что делает.** Путь клиента по M3: триггеры трёх типов, текущие решения в порядке, в каком их пробуют, точка слома по трём признакам, путь от слома в обе стороны, таблица инсайтов.

**Вход.** ТЗ, контекст проекта: обращения в поддержку, опросы при отмене, записи демо, интервью. Желательно — разбор альтернатив.

**Выход.** Карточки триггеров и точки слома, путь, таблица инсайтов не меньше пяти строк. Файл `src-path.md`.

**Какую дыру закрывает.** Неизвестно, когда: что запускает поиск решения и в какой момент терпеть уже нельзя.

**Сначала внутренние данные, потом веб** по `web-protocol.md`: чаты, форумы, отзывы 2–3★, сезонность запросов, вакансии, тендеры. До двадцати запросов.

**Когда не вызывать.** Путь по этому сегменту уже есть в контексте и ему меньше квартала.

**Цена.** Средняя.

**Признак провала.** Триггер — желание, а не событие. Момент — «в любой момент». Слом без последствий.

### market-sizing

**Что делает.** Оценка рынка: сколько компаний в сегменте, сколько они уже платят за смежное и достижима ли цель из ТЗ. Обратный счёт из M11: цель ÷ чек = нужно клиентов, сверка с числом компаний. Снизу вверх, диапазонами, с метками уверенности.

**Вход.** ТЗ: сегмент, география, цель в цифрах и срок. Желательно — разбор консультанта и внутренние данные из контекста: клиентская база по сегментам, биллинг, воронка с конверсиями.

**Выход.** По каждой нише: число компаний, чек, нужное число клиентов, доля сегмента как явное допущение, вердикт «достижимо / на грани / недостижимо», чувствительность. Файл `src-market-size.md`.

**Какую дыру закрывает.** Неизвестно, сколько компаний в сегменте, сколько они платят и хватит ли их на цель.

**Внутренние данные — первыми, если есть**: свой чек, свои клиенты в сегменте, конверсия — вместо допущений. **Веб** — для размера сегмента и расходов на смежное, по `web-protocol.md`: статистика и реестры, отраслевые ассоциации, проверенные отчёты, цены смежных продуктов, тендеры, вакансии как стоимость замещающей альтернативы. До двадцати пяти запросов.

**Когда не вызывать.** В ТЗ нет ни цели в цифрах, ни вопроса о масштабе. Сегмент не определён даже примерно — сначала target-audience-analyst.

**Цена.** Высокая: много веб-поиска.

**Признак провала.** Точечные оценки без диапазонов. Размер сверху вниз из одного отчёта. Доля сегмента без пометки «допущение». Все ниши «достижимы». Внутренние данные были, а расчёт только по открытым.

**Сигнал для оркестратора.** Цель недостижима во всех нишах — это расхождение с ТЗ: остановка и вопрос человеку с обоснованным диапазоном достижимого.

**Две формы обратного счёта.** Оценка рынка — одна из двух допустимых форм. Другая — расчёт внутри плана проверки, когда узкое место не размер рынка, а своя конверсия и чек. Тогда market-sizing не вызывается, а в логе записано, почему.

### synthetic-interviews — старт с чистого листа

**Место в маршруте.** Не выбирается оркестратором. Вызывается только если в ТЗ стоит режим «старт с синтетики» — его предлагает диспетчер при полноте 0–1, решает человек на согласовании. Тогда — сразу после консультанта.

**Что делает.** Интервью с синтетическими представителями потенциальной аудитории, чтобы было от чего оттолкнуться, когда данных о носителе нет совсем.

**Вход.** Описание предполагаемой аудитории и проблемы из ТЗ, разбор консультанта.

**Выход.** Стартовый материал о носителе: как он может описывать задачу, текущее решение, возражения. Каждый фрагмент помечен `[синтетика]`. Файл `src-synthetic.md`.

**Главное правило.** Синтетика никогда не засчитывается как опора. С синтетическим респондентом ничего не случалось — правило свидетельства её не пропускает. Гипотезы, выросшие из синтетики, получают метку «опоры нет» и идут в план первыми — на проверку живыми людьми. Синтетика ломает чистый лист, но ничего не подтверждает.

**Не закрывает никогда** дыры о фактах рынка: размер, число компаний, бюджеты, цены, конкуренты. Пустой контекст проекта — не повод для синтетики: факты ищутся в сети.

**Цена.** Средняя.

**Признак провала.** Все синтетические респонденты согласны с исходной идеей — это эхо, а не материал.

## Приоритеты

Порядок закрытия дыр из GAP — тремя слоями, как у менеджера проекта.

1. **Зависимости — жёсткий фильтр.** Дыра блокирующая, если без неё у следующего нужного скилла нет обязательного входа (поле «Вход — обязательно»). Блокирующие закрываются первыми, независимо от важности.
2. **Риск.** Среди незаблокированных первой идёт дыра, связанная с самым рискованным допущением из разбора консультанта.
3. **Стоимость — тай-брейк.** При равном риске сначала дешёвый скилл (поле «Цена»).

В логе каждое решение объясняется по слою, который его определил: «закрываю X, потому что оно блокирует Y», «потому что за ним главное допущение», «потому что дешевле».

## Готовность

Диспетчер выбирает в ТЗ один из пяти типов выхода. Тип задаёт точку финиша маршрута.

| Тип выхода | Когда | Финиш |
| --- | --- | --- |
| Разбор | нужна только оценка | после консультанта |
| Гипотезы | нужно понять, что делать | после проверки по сути |
| План проверки | нужно довести до действий | после набора для проверки |
| Вердикты по проверке | принесли результаты живой проверки | после сверки, или после проверки по сути, если были переформулировки |
| Аудит гипотез | человек принёс свои гипотезы: проверить и усилить | после повторной проверки по сути |

Готовность проверяется механически: типовой чек-лист плюс условие из ТЗ, если оно есть. Модель не оценивает, «хорошо ли получилось», — только сверяет пункты.

### Типовые чек-листы

**Разбор**
- названо хотя бы одно слабое место как разрыв логики, а не категория
- есть самое рискованное допущение
- есть вектор: одно-два направления без конкретных решений
- есть вопрос, который проверить первым

**Гипотезы**
- не меньше трёх прошли гигиену A и B
- у каждой есть опровергающее наблюдение
- каждая привязана к пункту GAP
- не больше половины под одной рамкой
- если был вектор — есть контрольная гипотеза
- у каждой гипотезы есть вердикт проверки по сути с основанием
- хотя бы одна гипотеза сужена или получила замечание — или объяснено, почему нет

**План проверки**
- каждая задача привязана к конкретной гипотезе
- у каждой гипотезы есть метод проверки, критерий успеха и критерий отсечения
- порядок проверки объяснён через зависимости или риск
- риски названы
- есть набор для проверки: материалы под метод каждой гипотезы и заготовки результатов, поля которых совпадают с критериями плана
- если в TO-BE цель в цифрах — есть обратный счёт в одной из двух форм: оценка рынка или формула цели с неизвестными и проверками, которые их заполнят

**Вердикты по проверке**
- у каждой гипотезы из плана есть вердикт — включая «недостаточно данных»
- каждый вердикт стоит на сигнале: числа или дословная реакция
- критерии взяты из плана без изменений
- дефекты проверки проверены по M7
- для «переформулировать» — если был генератор, новые гипотезы опираются на результаты

**Аудит гипотез**
- у каждой исходной позиции есть итог: у гипотез — держится, усилена или отклонена; у утверждений-оснований — подтверждается, не подтверждается или не проверено
- есть блок «про набор целиком»: зависимости, правило решения, метод проверки, что первым — со статусом после проверки
- уверенность нигде не выросла без названного нового источника
- у каждой усиленной — пара «было → стало» и из какого вердикта следует изменение
- усиленные версии прошли гигиену и повторную проверку по сути
- отклонённые перечислены с причиной
- новых гипотез, которых человек не приносил, в результате нет

**Для любого типа выхода**
- лог целый: у каждого шага заголовок и результат, номера подряд
- артефакты без вступлений и пересказа прочитанного — только формат выхода скилла

### Условие из ТЗ

Диспетчер может добавить своё условие готовности, только в наблюдаемой форме: должно быть понятно, какой факт в результате его подтверждает. По тому же правилу, что фальсифицируемость в гигиене.

- «гипотезы должны быть сильными» — не принимается
- «у каждой гипотезы метод проверки не требует разработки» — принимается

Условие видно человеку при согласовании ТЗ.

## Сдача

**Успешный финиш.** Результат плюс короткая сдача — в конце блок «Перенесено в контекст»:
- чек-лист готовности по пунктам со статусом каждого
- маршрут — одна строка на шаг: какой скилл и по какому слою приоритета выбран
- что осталось незакрытым в GAP

**Остановка по правилу** — лимит шагов, два промаха подряд или финальный чек-лист не сошёлся. То же самое плюс причина остановки.

**Замечания к системе** — последний блок любой сдачи: что оркестратор заметил про скиллы и реестр по ходу. Правки скиллов посреди задачи не делаются и не предлагаются.

**Продолжение — только через ТЗ.** Диспетчер пересобирает ТЗ с учётом того, что выяснилось: сузить задачу, сменить тип выхода, поправить условие готовности. Человек согласует — маршрут продолжается с места остановки с новым бюджетом. Продолжения «ещё на пару шагов» без правки ТЗ нет: остановка почти всегда значит, что ТЗ было слишком широким или ожидание неверным.

**Перенос в контекст проекта** — автоматически, в конце маршрута. В контекст переходят только материалы источников (`src-*`) и результаты живой проверки из `04-results.md`, в `context/from-tasks/`, с шапкой: какой скилл, какая задача, дата, тип материала. Текст гипотез, вердикты кабинетной проверки, планы и синтетика не переходят никогда.
