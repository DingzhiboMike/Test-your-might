# Что передать исполнителю

Читается перед вызовом исполнителя — только строка этого исполнителя. Модель и инструменты роли — в `.claude/agents/<имя>.md`, контракт — в его `SKILL.md`.

- **hypothesis-generator** — ТЗ есть, Шаг 0 пропустить; передать слабые места и вектор консультанта; все `src-*` ходов по линзам — как сырьё: генератор строит и из них, а не только из слабых мест; если были синтетические интервью — их анализ; если был разбор альтернатив — карту и разборы противников; если была оценка рынка — вердикты по нишам: гипотезы строятся только для «достижимо» и «на грани»; при модели предмета — `00m-model.md` и `00r-limits.md`, и в каждой гипотезе строки «Клетка», «Рамка продукта» (R-номер или «не требует: причина») и «Размер группы» с числом и источником; после шага `python3 scripts/check_chain.py tasks/<папка>`, ошибка — один перезапрос с отчётом `checks/chain.md`; механика, которой нет в рамках («нет»), гипотезой не становится
- **market-analyze, target-audience-analyst** — план поиска не согласовывать: вернуть его в резюме и сразу искать; в лог план пишешь ты
- **customer-path** — ТЗ, контекст проекта, разбор альтернатив, если был. Нужен генератору для рамок «триггер» и «точка слома» и проверке по сути — для вопроса «вписывается ли в точку слома»
- **test-kit** — план проверки `03-plan.md`, ТЗ, разбор консультанта и путь клиента, если был. Вызывается после планировщика, когда тип выхода — «план проверки»; это финиш маршрута. В шаблоне вызова, кроме `03b-test-kit.md`, разреши ему писать заготовки в `tasks/<папка>/results-templates/` — это единственное исключение из «больше никаких файлов». После вызова проверь, что в `results/` он ничего не создал
- **Обратный счёт — две допустимые формы.** Если в TO-BE есть цель в цифрах, обратный счёт обязателен, но выполняется одним из двух способов. Оценка рынка до генерации — когда вопрос в том, хватит ли людей или компаний. Или расчёт внутри плана проверки — когда узкое место не размер рынка, а собственная конверсия и чек, которые без живой проверки не узнать: тогда план содержит формулу цели с неизвестными и то, какая проверка заполнит каждое. Какую форму выбрал и почему — в лог.
- **market-sizing** — ТЗ с сегментом, целью в цифрах и сроком; разбор консультанта. Если в TO-BE есть цель в цифрах (выручка, ARR, число клиентов), дыра «достижима ли цель» связана с риском — ставь её рано: генерировать гипотезы по нишам, которые не вытянут цель, бессмысленно
- **alternatives-analyst** — ТЗ и контекст проекта; сначала внутренние данные о потерях, потом веб; результат нужен генератору для рамки «альтернатива» и проверке по сути для вопроса «что перевешивает»
- **hypothesis-validator** — гипотезы от генератора, ТЗ, указатель методологии; сверка с вебом по триггерам обязательна. Строку ПОЗИЦИЯ из ТЗ передавай как утверждение для проверки. Пункты GAP, которые ты оставил на его веб-сверку, передавай так же, как источнику: вопрос и критерий ответа до поиска — по каждому. При модели предмета проверяй цепочку: группа клетки, доступность механики по `00r-limits.md`, размер группы; факты берутся из клеток модели, сырой текст — только по ссылке на строку
- **research-report** — только на финише типа «исследование», один раз. Передай ТЗ, все `src-*`, `sources.csv`, `numbers.csv`, `checks/trust.md` (свежий, после `trust_map.py`) и журналы запросов из лога. Результат — `06-research.md`. Перечни «какие отчёты без чисел», «какие классифицированы» в указании не пиши по памяти: ссылайся на таблицу в `src-*`, где они уже сведены. Добавь фразу: «наборы с разными условиями (разные значения ожидания, допущения вместо данных) не склеивай, считай по каждой оси отдельно»
- **interview-analyst → interview-synthesis** — разборы запускай параллельно, по подагенту на файл; вся пачка — один шаг бюджета. Разборы по одному идут первыми, по файлу на интервью; сводку зови, когда разобрано два интервью и больше. Ей передаёшь все `src-interview-*.md`, ТЗ и реестр источников: она пересчитывает «k из n» по транскриптам, а не по разборам
- **project-analyst** — гипотезы с вердиктами «держится на бумаге» и «сузить», в суженной форме; без опоры или с разрывом выводимости — в план первыми. План — по карточке гипотезы из M4 (через `tools-index.md`): для каждой гипотезы метод проверки из M7 — показать формулировку, тест в скрипте продавца или микротест в рекламе, — выборка, срок, **критерий успеха в числах и критерий отсечения**. Критерии помечаются как «записаны до проверки»: по ним потом работает сверка результатов, и без них петля не замкнётся
