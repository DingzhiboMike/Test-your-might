# Полигон гипотез

Агентская система для проверки продуктовых и маркетинговых идей. Диспетчер, оркестратор и исполнители — отдельные агенты со своими ролями: один понимает задачу, другой ведёт её до результата, остальные разбирают, ищут, проверяют и собирают итог.

**Для чего.** Ты приносишь идею и просишь её провалидировать. Система раскладывает идею на утверждения, которые должны быть правдой, чтобы она сработала, и проверяет каждое по твоим материалам и по сети. Ты получаешь один документ: что в идее не так, где она слаба и как её усилить. Если без внутренних данных вопрос не закрыть, документ называет возможные объяснения и метод проверки, который покажет, какое из них верно.

## Как система проверяет идею

1. **Читает контекст.** Диспетчер помечает каждый файл в `context/`: прямая речь клиента, данные или утверждение команды, автор, дата. Затем отдельный агент читает всё целиком и по каждому вопросу ТЗ выписывает, что уже известно — дословно, — что противоречит и чего нет; скрипт проверяет, что ни один файл не пропущен. Доказательством служат слова клиентов, данные и случившееся; бриф команды и твоя собственная позиция проверяются наравне с идеей.
2. **Раскладывает идею.** По этой карте и по рамке решения из ТЗ (какие варианты на столе) консультант формулирует 5–8 утверждений, которые должны быть правдой, чтобы идея сработала, и отмечает те, без которых она падает. Дальше каждое проверяется отдельно.
3. **Ищет за и против.** Сначала твои материалы, потом сеть — отзывы, форумы, страницы конкурентов, отчёты. Под каждое утверждение есть запрос, который мог бы его опровергнуть. Три пересказа одной статьи считаются одним источником.
4. **Оставляет след.** Фрагмент, на котором стоит вывод, приводится дословно со ссылкой, и скрипт сверяет его с текстом источника. Число — с источником, периодом и формулой, если оно посчитано.
5. **Разводит роли.** Утверждения проверяет другой агент, не тот, что их сформулировал. Ещё один, в своём контексте, смотрит, держит ли фрагмент сделанный из него вывод.
6. **Называет неизвестное.** Исход по утверждению — подтверждается, опровергается или нет данных. Для «нет данных» — возможные объяснения, что косвенно говорит за каждое и какие данные покажут, какое верно.
7. **Копит знание.** Материалы источников и результаты живых проверок возвращаются в `context/` для следующих задач. Выводы самой системы туда не попадают, чтобы в следующий раз она не приняла их за доказательство.

## Что внутри

- `AGENTS.md` — инструкции для агентов: роли, принципы, правила. Главный документ: если что-то расходится, прав он.
- `CLAUDE.md` — одна строка `@AGENTS.md`: Claude Code читает только свой файл.
- `.claude/skills/` — двадцать один скилл, по одному на роль. Что каждый умеет и когда его звать — `.claude/skills/orchestrator/registry.md`.
- `methodology/` — `tools-index.md` (указатель инструментов методологии), `modules/` (модули M0–M8, M11–M13 и модули Э «Эксперименты», Д «Запрос данных», К «Критическое чтение источников», О «Оценки и чувствительность», П «Оффер и промо», Ж «Жизненный цикл и коммуникации», С «Сегментация и границы категории»), `web-protocol.md` (протокол работы с вебом).
- `context/` — материалы о продукте и клиентах, которые кладёшь ты.
- `tasks/` — задачи; папки создаёт система. Ни `context/`, ни `tasks/` в git не попадают.
- `scripts/` — проверки, которые не зависят от честности агента, и хуки Claude Code (`scripts/hooks/`, `.claude/settings.json`).
- `tests/` — выдуманные задачи для тестов отдельных навыков (`tests/fixtures/`) и лестница тестов по цене (`tests/README.md`).
- `docs/` — схемы системы (три PNG).
- `system-notes.md` — журнал замечаний к системе.

## Методология

Методология — модули в `methodology/modules/` и указатель `methodology/tools-index.md`: по типу пункта пути он говорит, какой инструмент брать и какому исполнителю его передать. Исполнитель читает только указанный раздел, а не модуль целиком.

| Модуль | О чём |
| --- | --- |
| M0–M8 | клиент и его задача, интервью и четыре силы, путь клиента и точка слома, несвершившиеся сделки и конкуренты, позиционирование, сообщения, проверка формулировок и цены, каналы |
| M11–M13 | дерево целей и обратный счёт, запуск и тиринг, рост |
| Э | эксперименты: нужен ли тест, план до запуска, чувствительность, порядок проверок, исходы, множественность |
| Д | запрос данных: шаблон с метрикой, зерном и сверкой, паспорт выгрузки |
| К | критическое чтение источников: паспорт источника, красные флаги статистики, отчёты вендоров |
| О | оценки и чувствительность: оценки Ферми, диапазоны, порядок влияния параметров (`scripts/sensitivity.py`) |
| П | оффер и промо: карточка оффера, инкрементальность, окупаемость акции |
| Ж | жизненный цикл и коммуникации: этапы, активация, удержание, триггерные цепочки |
| С | сегментация и границы категории: сегмент по задаче, слои B2B, проверка сегмента |

Разделы без источника в модулях помечены «синтез, проверять на данных»: система не выдаёт их за проверенное знание.

## Кто что делает

| Роль | Задача |
| --- | --- |
| Диспетчер | Превращает запрос в ТЗ: что ты хочешь получить, чего не хватает, какой результат будет на выходе. Задаёт три вопроса о том, что важнее всего уточнить (и четвёртый, необязательный: прогнать ли репетицию теста на синтетических респондентах — дольше и дороже). Исполнителей не выбирает |
| Человек | Отвечает на вопросы диспетчера (три, а при необходимости четвёртый) и согласует ТЗ — одним сообщением. Это единственная пауза в системе |
| Оркестратор | Строит маршрут: какого исполнителя звать на каждый пункт пути консультанта, в каком порядке, когда остановиться. Для шага-источника записывает инструмент методологии из указателя (`tools-index.md`). После каждого шага пересматривает, запускает проверки и ведёт лог |
| Исполнители | Разбор материалов (что уже известно из контекста, по каждому вопросу ТЗ), консультант (первый разбор и путь от AS-IS к TO-BE — что должно стать известно; разбор идеи на утверждения; итоговая позиция), генератор гипотез, проверка по сути, планировщик, набор для проверки, восемь источников данных (в том числе разбор экспериментов), проверка смысла, сборщик итогового документа (исследование или валидация), писатель брифа, синтетика, сверка результатов |

К источникам данных оркестратор ходит по выбору: только когда без ответа гипотезы или вердикт будут догадкой. Если ответ лежит внутри компании — воронка, выгрузка, итоги прошлой кампании, — система не ищет его в сети: оркестратор пишет запрос аналитику и кладёт его в итоговую сводку отдельным блоком.

## Что можно получить

Что нужно, выбирает диспетчер по запросу, а ты подтверждаешь в ТЗ.

| Результат | Когда | Что на выходе |
| --- | --- | --- |
| Разбор | нужна оценка идеи или постановки | разбор консультанта |
| Гипотезы | нужно понять, что делать | гипотезы с вердиктами проверки и итоговая позиция: на что ставить и с чего начать |
| План проверки | нужно довести до действий | план и готовые материалы для живой проверки |
| Вердикты по проверке | принёс результаты живой проверки | вердикты по плану прошлой задачи |
| Валидация | принёс свою идею или гипотезы: «провалидируй» | документ `06-validation.md`: вердикт по идее, утверждения с «за» и «против» из твоих материалов и сети, что не так, где слабо и как усилить, как проверить, карта доверия |
| Исследование | нужно понять, что известно, без выбора решения: «собери исследование» | отчёт `06-research.md`: ответ по каждому вопросу, основания, стороны, карта доверия |
| ТЗ на доработку | нужно оценить идеи и наполнить их конкретикой: «составь ТЗ аналитику и редактору» | три коротких документа, с которыми можно сразу идти к людям: задача аналитику, бриф редактору со словами клиентов, список решений за тобой |

Первым пунктом в списке вопросов ТЗ стоит твой вопрос твоими словами. Строка «ЭКСПЕРИМЕНТ» говорит, нужен ли вообще запуск теста, хватит ли решения на имеющемся или сначала нужна дешёвая замена. Если ТЗ ведёт к живой проверке, диспетчер добавляет необязательный четвёртый вопрос: прогнать ли репетицию скрипта на синтетических респондентах (дольше и дороже; результат ничего не доказывает, а ловит наводящие вопросы). Ключевые пункты помечены `[ключевой]`: по ним система ищет глубже. Решение, которое ты назвал принятым, помечено `[принято]` — система его не оспаривает и проверяет только допущения внутри. Строка «ЧТО ПОЛУЧИШЬ» заранее говорит, что будет в результате и где предел: какие вопросы без твоих данных останутся открытыми и чем их закрыть.

## Словарь

- **GAP** — список того, чего не хватает до цели; из него собираются вопросы задачи.
- **Опора** — то, на чём стоит вывод: дословный фрагмент интервью, данные, случившееся. Утверждение команды опорой не считается.
- **Карта доверия** — раздел итогового документа: что держится на нескольких независимых источниках, что на одном, что стоит проверить руками.
- **Сдача** — итоговая сводка после прогона: результат, что не закрыто, запросы данных аналитику.

## Проверки

Что можно проверить скриптом, проверяет скрипт. После каждого шага оркестратор запускает их одной командой — `check_step.py`. Проверку смысла делает отдельный агент в своём контексте: по вердиктам проверки по сути, по итоговому документу и по источнику, на котором стоит ключевой пункт пути. Перед окончанием ответа Stop-хук ещё раз прогоняет цитаты и числа и не даёт закончить, пока ошибки не исправлены или не перечислены.

| Скрипт | Что делает |
| --- | --- |
| `add_source.py` | регистрирует источник задачи в `sources.csv`, сохраняет сырой текст; страницу скачивает сам (`--fetch`) |
| `check_quotes.py` | цитата «…» [F-id] должна найтись в сыром тексте именно своего источника; считает, сколько источников не пересказывают друг друга; замечает цитаты без id, ссылки вне реестра, опору на утверждения команды |
| `add_number.py` | регистрирует число в `numbers.csv`: факт — с фрагментом в источнике, производное — только формулой с пересчётом, допущение — с причиной |
| `check_numbers.py` | число рядом со ссылкой [N-id]; разные значения при одинаковых условиях — противоречие, при разных — нет |
| `check_artifact.py` | артефакт шага не пуст и не заменён резюме; исполнитель не тронул чужие файлы; на блокирующие замечания проверки смысла есть ответы; блок счёта опор перенесён дословно |
| `list_unused.py` | источники, найденные на шаге, но не процитированные: вход для проверки смысла |
| `trust_map.py` | считает опоры для карты доверия |
| `review_format.py` | общий разбор отчёта проверки смысла и ответов автора: им пользуются `check_artifact.py` и `trust_map.py`, счёт не расходится |
| `check_private.py` | персональные данные (имена из `private.txt`, телефоны, e-mail, ИНН, карты) в артефактах и в логе; закрытые для веба слова из `closed-web.txt` в журналах запросов; найденное в отчёт не копируется |
| `check_step.py` | все проверки после шага одной командой: `check_artifact`, `check_quotes`, `check_private`, `check_numbers`; одна строка для лога со счётчиками, подробности — только по ошибкам |
| `check_knowledge.py` | разбор материалов: каждый файл контекста в таблице покрытия, по каждому пункту GAP есть раздел и «чего нет» |
| `check_path.py` | каждый пункт GAP привязан к пути консультанта или стоит «вне пути» с причиной; с `--plan` — каждый вариант решения покрыт, есть пункт на проверку допущения; перед сдачей — у каждого пункта пути есть исход |
| `check_log_sources.py` | у каждого шага-источника в логе записаны вопрос, зачем он нужен и что по нему уже известно; указан инструмент методологии из указателя (или «—») |
| `check_fresh.py` | старый веб-источник процитирован с годом |
| `check_long_list.py` | отсев длинного списка гипотез по правилам, записанным заранее |
| `check_env.py` | что установлено для чтения файлов и доступна ли сеть |
| `trust_block.py` | вспомогательный модуль: блок «СЧЁТ ОПОР», который переносится в отчёт дословно, не разбирается проверками чисел и свежести |
| `polygon.py` | полигон: выдуманные отчёты об экспериментах с ключом ответов и сверка навыка разбора экспериментов (без нейросети) |
| `sensitivity.py` | чувствительность формулы из реестра чисел: какой параметр сильнее всего двигает итог (методология О) |
| `fixture.py` | выдуманные готовые артефакты для тестов навыков: развернуть задачу до нужного шага |
| `check_readable.py` | документы для людей — брифы, итоговая позиция, документ валидации — читаются без знания системы: нет номеров гипотез, слов системы, кодов выгрузок; соблюдены лимиты размера |
| `check_publish.py` | перед отправкой на GitHub ищет в файлах и сообщениях коммитов имена и закрытые слова из задач и из `.publish-stopwords`; нашёл — отправка останавливается |
| `hooks/guard_writes.py` | хук: подагентам закрыта запись в систему, реестр и `context/` |
| `hooks/stop_check.py` | хук: проверка цитат и чисел перед окончанием ответа |
| `selftest.py` | самопроверка всех скриптов |

## Чтение файлов

`add_source.py` читает `.docx`, `.xlsx`, `.pptx`, `.pdf`, текст и страницы по адресу. С PDF помогают необязательные пакеты из `requirements.txt` (`pip install -r requirements.txt`): PyMuPDF и pypdf читают текст, PyMuPDF ещё выгружает страницы в картинки. Слайды-картинки и сканы без текстового слоя скрипт отклоняет с подсказкой: `scripts/pdf_to_images.py` сохраняет страницы, агент читает их и передаёт расшифровку с `--read partial`. Что установлено, показывает `python3 scripts/check_env.py`.

## Где запускать

| Среда | Инструкции | Скиллы |
| --- | --- | --- |
| Claude Code | `CLAUDE.md` → `AGENTS.md` | находит в `.claude/skills/` сам |
| OpenCode | `AGENTS.md` | находит в `.claude/skills/` сам |
| Codex, Cursor и другие | `AGENTS.md` | если среда не нашла скиллы — `AGENTS.md` велит читать их по пути напрямую |

Систему писали под Claude. На других моделях она работает, но результат зависит от того, справляется ли модель с длинными инструкциями. Агенты работают в отдельных контекстах только там, где среда даёт подагентов; без них все роли по очереди исполняет один агент, и правило «кто строит, тот не проверяет» выполняется не полностью.

## Как начать

1. Открой Claude Code в корне проекта, где лежит `AGENTS.md`: хуки и скиллы подгружаются оттуда. Если сменил папку посреди сессии, открой новую.
2. Положи в `context/` что есть о продукте и клиентах — что именно, написано в `context/README.md`.
3. `/dispatcher` и задача — или «диспетчер, …», если в среде нет слеш-команд.
4. Ответь на вопросы диспетчера (три; четвёртый — про репетицию теста — только если он применим) и согласуй ТЗ одним сообщением. Проверь, что первым пунктом стоит твой вопрос, и прочитай строку «ЧТО ПОЛУЧИШЬ». Дальше система идёт сама до сдачи.
5. После живой проверки возьми заготовки из `tasks/<задача>/results-templates/`, заполни и положи в `tasks/<задача>/results/`, потом напиши диспетчеру.
6. Запросы данных из сдачи отдай аналитику, ответ положи в `context/` и напиши диспетчеру: он пересоберёт ТЗ.

## Если правишь систему

- Хуки не дают править скиллы и скрипты по ходу задачи. Перед правкой создай в корне пустой файл `.polygon-dev`, после — удали.
- После любой правки в `scripts/` запусти `python3 scripts/selftest.py`.
- Один раз в своей копии включи проверку перед отправкой: `git config core.hooksPath scripts/git-hooks`. Свои закрытые слова — названия продуктов, компаний, партнёров — впиши в `.publish-stopwords` по одному в строке; файл в репозиторий не попадает.
- В репозиторий — только система. Примеры в инструкциях и тестах только выдуманные.
- Тесты по цене: сначала `python3 scripts/selftest.py` (бесплатно), потом полигон и один навык на фикстуре, всю цепочку — перед слиянием крупных правок (`tests/README.md`).
- Схемы — три PNG в `docs/`; исходника в репозитории нет, после изменений в системе их перерисовывают и заменяют (`docs/README.md`).
