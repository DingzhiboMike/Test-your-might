# Полигон гипотез

Агентская система для проверки продуктовых и маркетинговых идей. Диспетчер, оркестратор и исполнители — отдельные агенты со своими ролями: один понимает задачу, другой ведёт её до результата, остальные разбирают, ищут, проверяют и собирают итог. Цитаты, числа и права записи проверяют скрипты и хуки, а не исполнитель.

**Для чего.** Ты приносишь идею — например, «онбординг-чек-лист поднимет активацию пробного периода» — и просишь её провалидировать. Система раскладывает идею на утверждения, которые должны быть правдой, чтобы она сработала, и проверяет каждое по твоим материалам и по сети. Ты получаешь один документ: что в идее не так, где она слаба и как её усилить. Если без внутренних данных вопрос не закрыть, документ называет возможные объяснения и метод проверки, который покажет, какое из них верно.

## Что внутри

- `AGENTS.md` — инструкции для агентов: роли, принципы, правила. Главный документ: если что-то расходится, прав он.
- `CLAUDE.md` — одна строка `@AGENTS.md`: Claude Code читает только свой файл.
- `.claude/skills/` — девятнадцать скиллов, по одному на роль. Что каждый умеет и когда его звать — `.claude/skills/orchestrator/registry.md`.
- `methodology/` — указатель GTM-курса, модули курса, протокол работы с вебом.
- `context/` — материалы о продукте и клиентах, которые кладёшь ты.
- `tasks/` — задачи; папки создаёт система. Ни `context/`, ни `tasks/` в git не попадают.
- `scripts/` — проверки, которые не зависят от честности агента, и хуки Claude Code (`scripts/hooks/`, `.claude/settings.json`).
- `system-notes.md` — журнал замечаний к системе.

## Кто что делает

| Роль | Задача |
| --- | --- |
| Диспетчер | Превращает запрос в ТЗ: что ты хочешь получить, чего не хватает, какой результат будет на выходе. Задаёт три вопроса о том, что важнее всего уточнить. Исполнителей не выбирает |
| Человек | Отвечает на три вопроса и согласует ТЗ — одним сообщением. Это единственная пауза в системе |
| Оркестратор | После каждого шага решает, кого звать дальше, и ведёт лог. Первым всегда идёт консультант |
| Исполнители | Консультант (первый разбор, разбор идеи на утверждения, итоговая позиция), генератор гипотез, проверка по сути, планировщик, набор для проверки, семь источников данных, проверка смысла, сборщик итогового документа (исследование или валидация), писатель брифа, синтетика, сверка результатов |

К источникам данных оркестратор ходит по выбору: только когда без ответа гипотезы или вердикт будут догадкой. Если ответ лежит внутри компании — воронка, выгрузка, итоги прошлой кампании, — система не ищет его в сети: оркестратор пишет запрос аналитику и кладёт его в итоговую сводку отдельным блоком.

## Что можно получить

Что нужно, выбирает диспетчер по запросу, а ты подтверждаешь в ТЗ.

| Результат | Когда | Что на выходе |
| --- | --- | --- |
| Разбор | нужна оценка идеи или постановки | разбор консультанта |
| Гипотезы | нужно понять, что делать | гипотезы с вердиктами проверки и итоговая позиция: на что ставить и с чего начать |
| План проверки | нужно довести до действий | план и готовые материалы для живой проверки |
| Вердикты по проверке | принёс результаты живой проверки | вердикты по плану прошлой задачи |
| Валидация | принёс свою идею или гипотезы: «провалидируй» | документ `06-validation.md`: вердикт по идее, утверждения с «за» и «против» из твоих материалов и сети, что не так, где слабо и как усилить, как проверить, карта доверия |
| Исследование | нужно понять, что известно, без выбора решения: «собери исследование» | отчёт `06-research.md`: ответ по каждому вопросу, основания, стороны, карта доверия |
| ТЗ на доработку | нужно оценить идеи и наполнить их конкретикой: «составь ТЗ аналитику и редактору» | три коротких документа, с которыми можно сразу идти к людям: задача аналитику, бриф редактору со словами клиентов, список решений за тобой |

Первым пунктом в списке вопросов ТЗ стоит твой вопрос твоими словами. Ключевые пункты помечены `[ключевой]`: по ним система ищет глубже. Решение, которое ты назвал принятым, помечено `[принято]` — система его не оспаривает и проверяет только допущения внутри. Строка «ЧТО ПОЛУЧИШЬ» заранее говорит, что будет в результате и где предел: какие вопросы без твоих данных останутся открытыми и чем их закрыть.

## Словарь

- **GAP** — список того, чего не хватает до цели; из него собираются вопросы задачи.
- **Опора** — то, на чём стоит вывод: дословный фрагмент интервью, данные, случившееся. Утверждение команды опорой не считается.
- **Карта доверия** — раздел итогового документа: что держится на нескольких независимых источниках, что на одном, что стоит проверить руками.
- **Сдача** — итоговая сводка после прогона: результат, что не закрыто, запросы данных аналитику.

## Проверки

Что можно проверить скриптом, проверяет скрипт. После каждого шага оркестратор запускает их одной командой — `check_step.py`. Проверку смысла делает отдельный агент в своём контексте: по вердиктам проверки по сути, по итоговому документу и по источнику, на котором стоит главный вопрос. Перед окончанием ответа Stop-хук ещё раз прогоняет цитаты и числа и не даёт закончить, пока ошибки не исправлены или не перечислены.

| Скрипт | Что делает |
| --- | --- |
| `add_source.py` | регистрирует источник задачи в `sources.csv`, сохраняет сырой текст; страницу скачивает сам (`--fetch`) |
| `check_quotes.py` | цитата «…» [F-id] должна найтись в сыром тексте именно своего источника; считает, сколько источников не пересказывают друг друга; замечает цитаты без id, ссылки вне реестра, опору на утверждения команды |
| `add_number.py` | регистрирует число в `numbers.csv`: факт — с фрагментом в источнике, производное — только формулой с пересчётом, допущение — с причиной |
| `check_numbers.py` | число рядом со ссылкой [N-id]; разные значения при одинаковых условиях — противоречие, при разных — нет |
| `check_artifact.py` | артефакт шага не пуст и не заменён резюме; исполнитель не тронул чужие файлы; на блокирующие замечания проверки смысла есть ответы; блок счёта опор перенесён дословно |
| `list_unused.py` | источники, найденные на шаге, но не процитированные: вход для проверки смысла |
| `trust_map.py` | считает опоры для карты доверия |
| `review_format.py` | общий разбор отчёта проверки смысла и ответов автора: им пользуются `check_artifact.py` и `trust_map.py`, счёт не расходится |
| `check_private.py` | персональные данные (имена из `private.txt`, телефоны, e-mail, ИНН, карты) в артефактах и в логе; закрытые для веба слова из `closed-web.txt` в журналах запросов; найденное в отчёт не копируется |
| `check_step.py` | все проверки после шага одной командой: `check_artifact`, `check_quotes`, `check_private`, `check_numbers`; одна строка для лога со счётчиками, подробности — только по ошибкам |
| `check_log_sources.py` | у каждого шага-источника в логе записаны вопрос, зачем он нужен и что по нему уже известно |
| `check_readable.py` | документы для людей — брифы, итоговая позиция, документ валидации — читаются без знания системы: нет номеров гипотез, слов системы, кодов выгрузок; соблюдены лимиты размера |
| `check_publish.py` | перед отправкой на GitHub ищет в файлах и сообщениях коммитов имена и закрытые слова из задач и из `.publish-stopwords`; нашёл — отправка останавливается |
| `hooks/guard_writes.py` | хук: подагентам закрыта запись в систему, реестр и `context/` |
| `hooks/stop_check.py` | хук: проверка цитат и чисел перед окончанием ответа |
| `selftest.py` | самопроверка всех скриптов |

## Чтение файлов

`add_source.py` читает `.docx`, `.xlsx`, `.pptx`, `.pdf`, текст и страницы по адресу. С PDF помогают необязательные пакеты из `requirements.txt` (`pip install -r requirements.txt`): PyMuPDF и pypdf читают текст, PyMuPDF ещё выгружает страницы в картинки. Слайды-картинки и сканы без текстового слоя скрипт отклоняет с подсказкой: `scripts/pdf_to_images.py` сохраняет страницы, агент читает их и передаёт расшифровку с `--read partial`. Что установлено, показывает `python3 scripts/check_env.py`.

## Где запускать

| Среда | Инструкции | Скиллы |
| --- | --- | --- |
| Claude Code | `CLAUDE.md` → `AGENTS.md` | находит в `.claude/skills/` сам |
| OpenCode | `AGENTS.md` | находит в `.claude/skills/` сам |
| Codex, Cursor и другие | `AGENTS.md` | если среда не нашла скиллы — `AGENTS.md` велит читать их по пути напрямую |

Систему писали под Claude. На других моделях она работает, но результат зависит от того, справляется ли модель с длинными инструкциями. Агенты работают в отдельных контекстах только там, где среда даёт подагентов; без них все роли по очереди исполняет один агент, и правило «кто строит, тот не проверяет» выполняется не полностью.

## Как начать

1. Открой Claude Code в корне проекта, где лежит `AGENTS.md`: хуки и скиллы подгружаются оттуда. Если сменил папку посреди сессии, открой новую.
2. Положи в `context/` что есть о продукте и клиентах — что именно, написано в `context/README.md`.
3. `/dispatcher` и задача — или «диспетчер, …», если в среде нет слеш-команд.
4. Ответь на три вопроса диспетчера и согласуй ТЗ одним сообщением. Проверь, что первым пунктом стоит твой вопрос, и прочитай строку «ЧТО ПОЛУЧИШЬ». Дальше система идёт сама до сдачи.
5. После живой проверки возьми заготовки из `tasks/<задача>/results-templates/`, заполни и положи в `tasks/<задача>/results/`, потом напиши диспетчеру.
6. Запросы данных из сдачи отдай аналитику, ответ положи в `context/` и напиши диспетчеру: он пересоберёт ТЗ.

## Если правишь систему

- Хуки не дают править скиллы и скрипты по ходу задачи. Перед правкой создай в корне пустой файл `.polygon-dev`, после — удали.
- После любой правки в `scripts/` запусти `python3 scripts/selftest.py`.
- Один раз в своей копии включи проверку перед отправкой: `git config core.hooksPath scripts/git-hooks`. Свои закрытые слова — названия продуктов, компаний, партнёров — впиши в `.publish-stopwords` по одному в строке; файл в репозиторий не попадает.
- В репозиторий — только система. Примеры в инструкциях и тестах только выдуманные.
- Схемы: сначала правится `docs/architecture.html`, потом с него заново снимаются PNG (см. `docs/README.md`).
