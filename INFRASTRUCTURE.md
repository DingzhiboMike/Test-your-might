# Полигон гипотез: как устроено внутри

Для тех, кто разбирается в системе или правит её. Как пользоваться, написано в `README.md`. Если что-то здесь расходится с `AGENTS.md`, верен `AGENTS.md`.

## Как идёт задача

```
запрос человека
  → /dispatcher    ТЗ и от нуля до трёх вопросов по смыслу задачи
  → человек        отвечает и пишет «да»                     ← единственная плановая пауза
  → orchestrator   ставит профиль (route.py profile … level=auto), пишет его в log.md и state.json,
                   дальше ведёт маршрут по типу выхода
  → исполнители    подагентами, по одному артефакту на шаг
  → сдача          08-handoff.md (человеку), 08-sources.md (источники), 08-service.md (служебное)
```

После «да» в приложении Claude диспетчер открывает новую сессию с `/orchestrator tasks/<задача>`. Вручную оркестратора можно запускать, когда в `00-tz.md` есть строка `СОГЛАСОВАНО`.

Пока фоновый подагент работает, оркестратор заканчивает ход одной строкой и ждёт уведомления о завершении. Файлы через `sleep` не опрашивает: каждый опрос заново читает весь контекст. Если среда так не умеет, он ждёт результата в том же ходе.

## ТЗ

Поля: ЗАПРОС · ЦЕЛЬ · ЧТО ПОЛУЧИШЬ · GAP (не больше четырёх пунктов) · КОНТЕКСТ · ДОПУЩЕНИЯ · РЕШЕНИЕ · ВЕБ · ЗАКРЫТОЕ · СТАВКИ · НАГРУЗКА · ПРЕДМЕТ · ТИП ВЫХОДА · ТИР · ЁМКОСТЬ · РЕЖИМ · ПРОВЕРКА · ЦЕНА.

- В НАГРУЗКЕ всегда «уровень: авто» и ограничения, которые назвал человек.
- Пожелания (новые идеи, разведка поля, ширина, линзы, пробный прогон) стоят в РЕЖИМЕ. Спрашивает о них диспетчер, только когда ответ меняет задачу.
- Для валидации по умолчанию берётся Tier 2. Tier 1 — только если решение необратимо и дорого и человек просит сверить внешние числа с первоисточником или сравнить нескольких конкурентов.

## Профиль прогона

Уровней нагрузки нет. Есть один стартовый набор `auto`, остальное оркестратор решает по ходу. Решение, которое меняет обязательность шагов, он записывает командой `route.py profile` и строкой в логе «было → стало → почему». В заголовке каждого шага — строка «Если пропустить».

Инварианты, которые не отключаются:

- проверка по сути идёт отдельным агентом, при «ВЕБ: да» — с поиском;
- цитаты дословные, с id источника;
- персональные данные закрыты;
- критерии записаны до проверки;
- цель меняет только человек;
- у ключевого вопроса, на который может ответить сеть, есть поиск или строка «Без хода» с причиной;
- потолок вызовов не превышается.

| Параметр | Значения | Что меняет |
| --- | --- | --- |
| generation | narrow · medium · wide | ширина генерации; narrow — без линз, Нострадамуса и отсева идей |
| evidence | none · links · quotes | quotes по умолчанию; none и links — только по просьбе человека, проверка цитат тогда предупреждает, а не блокирует |
| validation | none · method · web · full | web по умолчанию; method — только если сеть закрыта; full — ещё проверка смысла и аудит |
| forecast | on · off | обязательны ли Нострадамус и отсев идей |
| lenses | 0–3 | сколько раз сходить за сырьём к источникам до генератора; число берётся из РЕЖИМА |
| data | none · context · public | какие данные читать |
| run | steps · solo | цепочка агентов или один агент `light-run` на весь тип «гипотезы» |
| reviewer | same · other · human | кто проверяет смысл и делает аудит: та же модель, более сильная того же производителя или ещё и человек |
| audit | off · on | аудит находок разбора материалов до генерации |
| ceiling | строка | потолок вызовов и модель |

Разбор значений — в `scripts/profile_lib.py`, что каждое снимает из обязательного, — функция `profile_keeps` в `scripts/route.py`. Задачи, созданные со старыми уровнями, читаются как есть. `.claude/skills/orchestrator/recipes.md` — примеры маршрутов из прошлых прогонов; их колонки light, work и strict означают глубину решения, а не уровень.

## Бюджет

В бюджет входят все вызовы маршрута. Свободная часть — шаги по тиру: восемь для Tier 1, шесть для Tier 2. Резерв — обязательные вызовы, которые оркестратор не выбирает. Потолок равен оценке вызовов, умноженной на 1,3; на нём система останавливается. Считает `scripts/cost_estimate.py`: `--detail` показывает, из чего сложилась оценка, `--left` — сколько осталось. Минуты и токены человеку не обещаются.

## Против лишнего расхода

- При валидации проверка по сути делает не больше 12 запросов и 4 страниц, в сеть идёт по ключевым утверждениям (`methodology/web-protocol.md`, раздел о бюджете запросов).
- Если в контексте один файл и это не интервью, при валидации разбор материалов не запускается.
- Опровержение, которое уже сделал источник данных, проверка по сути не повторяет.
- Усиления и план проверки не пересказывают вердикты: ссылаются на номер утверждения.
- Лимит слов артефакта называется исполнителю в вызове, чтобы документ не пришлось сокращать после проверки.
- Артефакты оркестратор читает по заголовкам и нужным строкам.

## Сдача

`08-handoff.md` начинается с раздела «Что я рекомендую сделать»: ответ на первый вопрос ТЗ, одно–три действия (у каждого «Отвечает на» и «Почему»), одна строка про цену, первый шаг и условие отказа, ссылка на раздел полного документа. В валидации следом идёт «Что убрать, что усилить, что оставить»; усиленная формулировка помечена как непроверенное предложение. Лимит слов задаёт `scripts/check_readable.py`: для валидации 1100, для остальных он зависит от профиля. Раздел «Что лежит в папке задачи» строит `handoff_index.py`, механическую часть `08-service.md` — `handoff_service.py`.

## Карта документов и модель предмета

Контекст читается в два слоя. Важность документов и надёжность выводов считают скрипты.

1. **Карта документов.** До согласования карту строят только скрипты, без подагентов: `map_docs.py` нумерует строки и размечает числа, срезы, продукт и риск, `map_summary.py` сводит это в таблицу для диспетчера. Свои слова продукта и рынка для разметки впиши в локальный `.map-terms` в корне (строки «срез: …», «продукт: …», «риск: …»).
2. **Модель предмета.** Нужна не всегда: имеет смысл от восьми документов, когда ключевому вопросу нужны клетки «группа × признак». Решает оркестратор. `document-mapper` описывает документы и цитирует по номерам строк, `check_map.py` проверяет дословность и полноту, `rank_impact.py` выбирает документы для углубления, `subject-model` выписывает клетки, `build_model.py` считает их надёжность. Консультант строит путь от пустых и слабых клеток, `check_chain.py` и `check_rank.py` проверяют, что гипотезы и порядок направлений на них опираются.

Без модели предмета материалы читает `context-reader`: по каждому вопросу ТЗ — что известно дословно, что противоречит и чего нет. `check_carry.py` следит, чтобы ключевая находка не потерялась до сдачи.

## Модели

Роли по умолчанию идут на sonnet. `document-mapper`, `brief-writer` и `test-kit` — на haiku. Opus по умолчанию не получает никто: его включают параметром `model`, при `reviewer=other` или когда sonnet отработал шаг и результат не годится; причина пишется в лог. Источник — `scripts/roles.py`: `--write` пересобирает описания агентов, `--check` сверяет.

## Поиск в сети

По умолчанию — встроенные WebSearch и WebFetch. Дополнительный движок объявляется локально в `.polygon-local.json`, порядок работы с ним — в `methodology/web-engines.local.md`; оба файла в git не попадают. Правила протокола от движка не зависят. Хук проверяет на закрытые слова запросы и встроенного, и объявленного движка. `add_source.py` не принимает за источник страницу блокировки и сообщение об ошибке загрузки.

## Что где лежит

| Путь | Что |
| --- | --- |
| `AGENTS.md`, `CLAUDE.md` | инструкции и принципы |
| `.claude/skills/` | диспетчер, оркестратор (`routes/` по типам выхода, `registry.md`, `calls.md`) и исполнители |
| `.claude/agents/` | модель и инструменты каждого подагента |
| `.claude/settings.json` | подключает хуки из `scripts/hooks/` |
| `scripts/` | проверки и маршрут в коде; перечень — `methodology/scripts-reference.md` |
| `scripts/hooks/` | `guard_writes` (права записи и сети), `step_gate`, `stop_check` (цитаты, числа и персональные данные перед концом ответа), `trace` (расход), `web_flag` (фразы для ИИ в ответах сети) |
| `methodology/` | модули, `tools-index.md`, `web-protocol.md`, реестр правил `rules.csv` |
| `context/` | материалы человека; `from-tasks/` — перенос из прошлых задач |
| `tasks/<задача>/` | ТЗ, лог, артефакты шагов, реестр источников, `state.json`, сдача |
| `evals/` | кейсы с известным ответом; счёт — `eval_score.py` |
| `docs/` | общая схема и её исходник |

Проверка установки: `python3 scripts/selftest.py`.

## Известные ограничения

- Проверка смысла и аудит — оценки модели. По умолчанию модель та же, что у авторов, и слепые пятна у них общие.
- Повторный прогон на тех же материалах может дать другие вердикты.
- Защитные хуки (`guard_writes`, `step_gate`, `stop_check`) при сбое блокируют действие. Но если сессия открыта в папке выше проекта, `.claude/settings.json` не подгружается и хуков нет; хук, превысивший таймаут Claude Code, среда не считает блокировкой; `.polygon-dev` снимает запреты, и создать его может любой, у кого есть запись в корень. Учётные хуки (`trace`, `web_flag`) при сбое намеренно пропускают.
- Подагент пишет артефакт, только пока шаг открыт. Перезапрос после ошибок открывает `route.py retry`, правку без исполнителя закрывает `route.py recheck`.
- Лимит запросов в сеть и правила против повторов записаны в инструкциях: скрипт их соблюдение не проверяет.
- `check_fresh` сверяет год источника по реестру, а не по странице.
- Одиночный проход (`run=solo`) расходится с инвариантом: оркестратору велено держать проверку по сути отдельной, а скилл `light-run` всё ещё пишет её сам и без поиска. Пока это не исправлено, проверку в таком проходе независимой считать нельзя.
- `reviewer=other` и `human` проверены только скриптами.
- Размер промежуточных артефактов не ограничен, и на длинных задачах он заметно влияет на время.
