# Evals — качество итоговых выводов

Скрипты системы проверяют форму: цитата есть в источнике, поле заполнено, число пересчитано. Пришла ли система к верному выводу, они не видят. Evals меряют именно это — на замороженных кейсах, где правильный ответ или исход известен заранее.

## Что лежит где

- `cases/<кейс>/` — выдуманные кейсы, в репозитории. Пример — `cases/example-sverka/`.
- `cases-local/<кейс>/` — настоящие кейсы из прошлых задач. Только локально (в `.gitignore`): по R-021 названия, числа и формулировки проектов в репозиторий не попадают.
- `results/` — отчёты прогонов, только локально.

## Кейс

```
<кейс>/
  request.md   — запрос к диспетчеру и ответы на его вопросы одним сообщением
  context/     — обезличенный контекст: кладётся в context/ проекта перед прогоном
  key.json     — ключ: чем меряется результат
```

`key.json`:

| Поле | Что это |
| --- | --- |
| `must` | выводы, которые должны найтись: `{"id", "pattern", "why"}` |
| `traps` | ловушки кейса — шаблон вывода, в который система может попасть: утверждение команды принято за факт, единичный случай за общее |
| `forbidden` | неприемлемые рекомендации |
| `outcome` | известный исход эксперимента: `text` и `contradicts` — шаблоны выводов, которые ему противоречат |
| `causal_min_roots` | сколько независимых корней опор нужно причинному выводу (по умолчанию 2) |
| `artifacts` | по каким файлам задачи искать; по умолчанию итоговые (`02c`, `02e`, `02f`, `03`, `06`, `07*`, `08-handoff`) |

Шаблоны — регулярные выражения без учёта регистра, ищутся по абзацам. Ключ пишется до прогона и после не правится: это те же критерии, что не двигаются (R-009). Шаблон, который не ловит верный вывод другими словами, правится с записью «было → стало → почему» в `request.md`, и все прошлые прогоны кейса пересчитываются.

Ключ — не эталонный текст. Совпадение слово в слово не нужно: меряется, назван ли верный механизм, не попала ли система в ловушку, не противоречит ли рекомендация известному исходу и стоит ли причинный вывод на двух независимых источниках.

## Прогон

1. Отдельная копия проекта (`git worktree add ../polygon-eval`), в её `context/` — содержимое `context/` кейса.
2. Диспетчеру — текст запроса из `request.md`, на его вопросы — ответы оттуда же. Дальше маршрут до сдачи как обычно.
3. Счёт:

```bash
python3 scripts/eval_score.py tasks/<папка задачи> evals/cases/<кейс>
```

Эксперт, если смотрел сдачу, добавляет свою оценку: `--expert "корректность=4 полнота=3 шаги=5"` (по пятибалльной шкале: верен ли вывод, всё ли важное названо, можно ли завтра сделать следующий шаг).

## Метрики

| Метрика | Считает | Хорошо |
| --- | --- | --- |
| полнота | доля `must`, которые нашлись | все |
| ловушки | сколько `traps` сработало | 0 |
| неприемлемые рекомендации | сколько `forbidden` сработало | 0 |
| противоречие исходу | абзацы с шаблоном из `outcome.contradicts` | 0 |
| причинные выводы без опоры | абзацы с «из-за», «приводит к», «потому что»…, где независимых корней меньше `causal_min_roots` | доля падает от версии к версии |
| завышенная уверенность | «уверенность: высокая» меньше чем на трёх корнях | 0 |
| оценка эксперта | `--expert` | — |

Один прогон — шум: модель недетерминирована. Сравнивай версии системы по 3–5 прогонам кейса и по нескольким кейсам; правку системы, после которой ловушки или противоречия исходу выросли, — откатывай или разбирай.
