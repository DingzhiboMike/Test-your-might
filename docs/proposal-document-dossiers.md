# Предложение (ред. 2): картография документов в диспетчере и модель предмета

Статус: внедрено — `map_docs.py`, `check_map.py`, `build_model.py`, `rank_impact.py`, `check_chain.py`, `check_rank.py`, скиллы `document-mapper`, `document-deepener`, `subject-model`, этап картографии в диспетчере, поля ГРУППЫ и РАМКИ ПРОДУКТА в ТЗ, правки консультанта, генератора, проверки по сути и позиции, реестр. Не сделано: аудит качества на втором наборе документов и полный прогон маршрута на реальной задаче. Ниже — исходное описание предложения; названия скриптов и файлов в нём могут отличаться от реализованных, актуальное — в `AGENTS.md` и реестре.

## 1. Проблема

Порядок сейчас: ТЗ → разбор материалов → консультант → генератор → проверка по сути → позиция. Ломается он в начале цепочки.

1. **Контекст превращается в банк цитат.** Фрагменты выписываются «по пунктам вопроса»; кто говорит, сколько их, слова это или поведение, остаётся неявным. Фрагменты про разные группы попадают в один вывод.
2. **Рамки предмета до генерации не фиксируются.** Что в продукте есть и чего нет, никто не записывает. Пожелание клиента становится «механикой».
3. **Выводы не выводятся из данных по порядку.** Проверка идёт по одной гипотезе, порядок в позиции ставится по числу «опор», критерий выбора из ТЗ нигде не считается.

Корень один: между «файлами» и «гипотезами» нет слоя, где видно, что известно, про кого, откуда и насколько надёжно.

## 2. Что показал пробный прогон по первой редакции

- **Описание документа работает.** Тип, группа, размер выборки, что измерено, дата, нечитаемое — дешёвые модели заполняют точно и честно помечают «не читается».
- **Оценка «что важно» не работает.** Правила с суждением модели пометили «важными» около четырёх пятых документов: фильтр не отсекает. Важность должна считаться скриптом по формуле из ТЗ, а не записываться в досье.
- **Модель пропускает числа и срезы,** которые документ выводит сам (доли, размеры групп, расчёты ниже по тексту), и выбирает слабую ключевую цитату (строка таблицы без базы).
- **Цитаты из таблиц склеиваются** и не проходят проверку на дословность.
- **Стоимость.** Параллельная пачка досье и углубление всего контекста стоят миллионы токенов; без предварительной оценки расхода и согласия человека так запускать нельзя.
- **Аудит разметки (слепое сравнение сильной моделью на 8 случайных документах, 64 поля):** существенных ошибок 1,6 %, цитат вне документа 0, пропущенных критичных фактов в среднем 1,0 на документ (порог «не более 1 на документ» нарушен в двух документах). Ошибки — почти всегда пропуск чисел и срезов, а не искажения.
- **Прототип скрипта разметки** (числа, срезы, продукт, риск по регулярным выражениям и таблицам) на независимой проверке по цитатам с цифрами из углублённых заметок поймал около 70 %; хуже всего таблицы. Скрипт ловит то, что модель пропускает.

## 3. Принципы

1. **Картография описывает документ и не оценивает его важность.** Важность считает скрипт по формуле из ТЗ.
2. **Три слоя на документ:** скрипт извлекает кандидатов → лёгкая модель описывает и выбирает из списка → скрипт проверяет.
3. **Фрагмент без указания, про кого он и что измерено, опорой не считается:** годится как идея, не как основание для выбора.
4. **Картография переиспользуется.** Описание документа не зависит от задачи; хранится по хэшу файла, пересчитывается только при изменении файла, схемы или модели.
5. **Рамки продукта и определения групп спрашиваются у человека,** а не выводятся из документов: это 10 минут человека вместо дорогого поиска.
6. **Модель знает, чего не знает.** Пустая клетка — результат.
7. **Порядок вывода задаёт критерий из ТЗ.** Ранжируется только то, что можно посчитать.

## 4. Новый порядок

```
ДИСПЕТЧЕР
  этап 1  КАРТОГРАФИЯ ДОКУМЕНТОВ    скрипт → лёгкая модель → скрипт-проверка; переиспользуется
  этап 2  ТЗ                        в ТЗ: группы, критерий выбора, РАМКИ ПРОДУКТА; противоречия документов
                                    выносятся человеку; три вопроса идут из пробелов карты
  согласование (единственная пауза)
ОРКЕСТРАТОР
  модель предмета                   матрица «группа × признак» из карты; важность — по формуле; углубление
                                    документов только по запросу модели (лимит по тиру)
  консультант                       путь = пустые и слабые клетки по влиянию на критерий
  источники / линзы                 заполняют клетки
  генератор                         гипотеза называет клетку, группу и строку рамок продукта
  проверка по сути                  проверка цепочки, а не отдельных фраз
  Нострадамус → отсев идей          как сейчас
  позиция                           ранжирование по критерию из чисел модели; иначе «не ранжируется»
  бэклог тестов
```

## 5. Картография документов (этап 1 диспетчера)

### 5.1. Слой 1 — скрипт (детерминированный, без модели)
- метаданные: формат, размер, хэш, дата файла; нечитаемые форматы помечаются сразу;
- очистка текста; таблицы по ячейкам (не склеивать ячейки в цитате);
- числа и срезы: доли и размеры групп с базой, «X / Y», p-значения, «N респондентов»;
- теги предложений: число, срез (сегмент, портрет, оборот, «новички», отток…), продукт (тариф, лимит, подписка, выгрузка, бонус…); слова своего продукта — в локальном `.map-terms`, риск («и так», «не окупится», «не значимо»);
- результат — список кандидатов с контекстом.

### 5.2. Слой 2 — лёгкая модель
Заполняет поля по жёсткой схеме. Выбирает из списка кандидатов, а не ищет сама. «Не указано» допустимо; выдумывать нельзя.

| Поле | Что пишется |
| --- | --- |
| Тип | отчёт о тесте / опрос / интервью / выгрузка / описание продукта / исследование / утверждение команды / другое |
| Про кого | группа, сегмент, оборот; «не указано» — ответ |
| Сколько | n, как в документе |
| Что измерено | слова / поведение / результат теста / описание / утверждение команды |
| Дата | период данных и дата публикации |
| Выводы документа | 2–3 пункта его же словами, без наших выводов |
| Числа и срезы | каждый размер группы и доля — с базой и разрезом; пустое поле допустимо только с пометкой «в документе нет» |
| Про продукт | что документ говорит о продукте, дословно |
| Риски и ограничения команды | если документ их записал |
| Ключевая цитата | фраза-вывод, не строка таблицы; одна непрерывная строка из одного абзаца или ячейки |
| Сверх схемы | до двух неожиданных фактов |
| Статус чтения | прочитан / частично / не читается |

Чего в карте нет: важности, выводов о причинах, связей между документами.

### 5.3. Слой 3 — скрипт-проверка
- цитаты дословны (`check_quotes`);
- покрытие файлов 100 %, нечитаемое помечено;
- полнота: каждое помеченное числовое предложение либо в поле «Числа и срезы», либо отброшено с причиной;
- формат полей, длины, обязательные поля.

## 6. Приёмка качества: аудит разметки

Выполняется при смене схемы, модели или правил скрипта.
1. Выборка 8–10 документов, случайная по типам, без нечитаемых.
2. Сильная модель читает документы и заполняет те же поля **не видя карты**, затем сравнивает.
3. Исходы по полям: совпало / минорное / существенное / пропуск / лишнее.
4. Пороги, записанные до проверки: существенных ошибок по полям не более 10 %; цитат вне документа 0; пропущенных критичных фактов не более 1 на документ.
5. Золотой набор: 10–15 фактов, которые человек знает наверняка; каждый должен быть в карте.

Результат аудита сохраняется рядом со схемой; пороги не двигаются по результатам.

## 7. Что диспетчер делает с картой
- вместо ручных паспортов файлов — паспорта из карты;
- противоречия между документами (числа, окна, определения) — в ТЗ, решает человек;
- пробелы карты — основа трёх вопросов: рамки продукта, определения групп, что принять допущением;
- заполняет в ТЗ: ГРУППЫ, КРИТЕРИЙ, РАМКИ ПРОДУКТА (с источником каждой строки и пометкой «подтверждает человек»).

## 8. Дальше по маршруту
- **Модель предмета.** Матрица «группа × признак»; в клетке значение дословно, группа источника, n, тип, свежесть, число независимых документов. Надёжность считает скрипт по правилам: «значение» — группа точная, n указан, тип поведение или тест; «версия» — соседняя группа, слова или n не указан; «идея» — один респондент или утверждение команды; «нет данных» — пусто. Данные про соседнюю группу пишутся как «версия из соседней группы», не склеиваются.
- **Важность** документа для задачи считает скрипт по четырём признакам из ТЗ (группа, вариант решения, рамки, число для критерия). Лимит углубления — по тиру (Tier 2 — до 8, Tier 1 — до 12) и по запросу модели предмета; допускается дозапрос до четырёх документов.
- **Консультант** строит путь от пустых и слабых клеток.
- **Генератор** обязан назвать клетку, группу и строку рамок продукта; цитата клиента может быть основанием, но не механикой.
- **Проверка по сути** проверяет цепочку: группа → механика → доступность в продукте → ожидаемый эффект → хватает ли людей → что покажет → какое решение закроет.
- **Позиция** ранжирует по критерию ТЗ только по клеткам с достаточной надёжностью; остальное — «не ранжируется, нужны такие данные».

## 10. Риски

| Риск | Как снять |
| --- | --- |
| Лёгкая модель пропустила факт, дальше его никто не увидит | скриптовый слой кандидатов; аудит; поле «сверх схемы»; ключевые документы читаются целиком |
| Карта выглядит авторитетно | статусы чтения и надёжности, метки «не читается» и «частично» |
| Подгонка документа под схему | только дословные цитаты, «не указано» допустимо |
| Противоречия между документами не видны при пофайловом чтении | отдельный шаг в модели предмета на сильной модели по всей карте |
| Сканы и картинки | отдельная очередь на сильную модель или человеку |
| Таблицы теряются в тексте | разбор таблиц по ячейкам в слое 1 |
| Расход растёт без контроля | оценка расхода до запуска, лимиты на углубление, согласие человека на пачку более трёх агентов |

## 11. Стоимость
Слой 1 бесплатный. Слой 2 — один проход на документ на лёгкой модели по очищенному тексту с фиксированной схемой; карта кэшируется по хэшу и повторно не считается. Сильная модель нужна на модель предмета, консультанта, генератор, проверку цепочки и позицию. Любой запуск пачки агентов сопровождается оценкой расхода.

## 13. Открытые вопросы
- Где хранить карту, если скиллы не пишут в `context/`: отдельная папка рядом с реестром задач или общий кэш по хэшу.
- Как задать группы в ТЗ, если человек их не знает: нужен вопрос диспетчера «по каким группам делим и откуда известно, кто в какой».
- Калибровка пороговых значений аудита на двух-трёх задачах.
- Нужен ли режим «быстрый проход» (до 10 документов, без углубления) для задач Tier 2.
